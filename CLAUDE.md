# Notes for Claude Code

Non-obvious stuff learned while building this. Don't re-derive these the hard way.

## UOB PDF parsing (`backend/src/app/parsing/uob/`)

- These statements have **no table gridlines** — columns are pure whitespace alignment. Don't reach for `pdfplumber.extract_table()`; it needs ruling lines. Instead: cluster words into physical lines by `top` proximity (`pdf_utils.group_into_lines`), then bucket each line's words into columns by hardcoded x-ranges calibrated against the real samples (see `pdf_utils.Column`).
- **Every page has a bilingual disclaimer footer** whose words fall inside the description column's x-range (e.g. "UOB Plaza Singapore" lands at x0≈128, inside the 100–330 description bucket). If you don't filter words by `top < FOOTER_TOP_CUTOFF` (780) *before* grouping into lines, footer text silently gets appended to whatever transaction was last on the page. This was a real bug — caught it by grepping parsed output for `"relation thereto"`.
- **Card statement `SUB TOTAL` is a running balance, not this statement's net.** It equals `PREVIOUS BALANCE + charges − credits`, not `charges − credits` alone. If you're cross-validating a parser against the printed total, you must include `PREVIOUS BALANCE` in the formula or every multi-month sample will look "wrong" when it isn't.
- **Card identity line vs. Summary table is a real false-positive trap.** The per-card `Summary` table near the top of page 1 also contains the card number as its own word — a naive "any line matching the card-number regex is the identity line" grabs the Summary row (wrong card name) instead of the true per-card identity line right above the transaction table. Fix: only resolve identity by searching *backward* from a confirmed `Post`/`Trans` header line, never by scanning forward for the number pattern.
- Account statement dates have no year (`"05 May"`) — derived from the `Period: ... to ...` line. Card statement dates have no year either (`"10 JUN"`) — derived from `Statement Date`, with `year -= 1` when a transaction's month is later than the statement's month (Dec/Jan wraparound).
- `BALANCE B/F`, `Total` (account statements) and `PREVIOUS BALANCE`, `SUB TOTAL`, `TOTAL BALANCE FOR ...` (card statements) are not transactions — they're excluded by exact-prefix text match, not by column heuristics.

## Which banks are supported is data, not copy (`parsing/base.py`)

- **`BankParser.parsing_implemented` is the single source of truth for "does this bank work yet".** UOB parses; `parsing/dbs/` and `parsing/ocbc/` are detection-only stubs (`parsing_implemented = False`) so an upload gets a precise "DBS detected, not supported yet" instead of a generic unrecognized-format error. `GET /api/settings` splits the two into `supported_banks` / `detected_banks`, and the UI reads those: the dashboard's first-run empty state (`bankListLabel` in `Dashboard.tsx`) and the Settings → Region card. The empty state used to hardcode "Upload a DBS, OCBC, or UOB e-statement", which claimed two banks that don't parse. Don't retype a bank list into user-facing copy — implementing a parser should flip every claim about it in one move.
- `registry.detect_and_parse`'s fallback error only names banks that can actually parse, since a detected-but-unimplemented bank raises its own more specific error before that line is ever reached.

## Sanitized sample PDFs (`backend/scripts/generate_sample_pdfs.py`)

- **Jan-Jun are pinned regression fixtures; Jul-Dec are the demo dataset.** The first six months are written out longhand in the generator and their totals/counts are asserted by name in `tests/test_sanitized_sample_parsers.py` - changing them breaks tests on purpose. The Jul-Dec months are built from row helpers (`nets`/`direct`/`paynow_out`/`salary`/`card_bill`/...) and exist so uploading the whole folder fills every chart in the UI; they're what `docs/screenshots/` is shot from. Two parameterized tests walk *whatever* is in the folder (each account statement reconciles against its own printed `Total` row, each card statement yields cards with transactions), so a month added later is covered the day it lands.
- `PDF Examples/` is an optional, gitignored local folder for testing against your own real statements - a fresh clone has none, and the tests that use it (`test_uob_account_parser.py`/`test_uob_card_parser.py`/`test_registry_and_pdf_io.py`/`test_statements_router.py`/`test_crud_routers.py`) discover files in it by glob and skip gracefully when it's absent, rather than hardcoding a filename. `PDF Examples (Sanitized)/` is synthetic and committed; `tests/test_sanitized_sample_parsers.py` runs against it unconditionally so `uv run pytest` always exercises the parsers even without real statements.
- The generator draws text with `reportlab.pdfgen.canvas` at the **exact same column x-positions** the parser's `Column` definitions expect (kept in sync manually - there's a comment pointing back at each parser file). That's what makes the output round-trip through the real parser correctly; it's not just a lookalike, it's parseable.
- Coordinate systems differ: pdfplumber's `top` is distance-from-page-top (what the parser's column ranges are calibrated against), reportlab's `y` is distance-from-page-bottom, ascending. The conversion used is `y = PAGE_H - top - font_size * 0.8` (approximates baseline offset) - exact pixel alignment doesn't matter, only that words on the same logical row land within 3pt of each other (the parser's line-grouping tolerance) and each column's x falls inside the right bucket.
- The multi-card statement fixture (`SampleCardStatement_MultiCard_Mar2024.pdf`) exercises a code path **no real sample ever covered** - two cards in one statement - and is what caught that the identity-line-vs-Summary-table backward-search fix actually works for a genuine multi-card case, not just the single-card real samples.
- `scripts/seed_demo_data.py` rebuilds the screenshot database from those PDFs (contacts and rules first - categorization runs at upload time, so a contact created afterwards owns nothing and reads $0 spend). Re-shoot `docs/screenshots/` from it at 1440x750 @2x, which is the 2880x1500 the committed images already use.
- Regenerate with `uv run python scripts/generate_sample_pdfs.py` (`reportlab` is a dev dependency). If you change a parser's column x-ranges, the generator's constants (`ACC_*`/`CARD_*` at the top of the script) need to move with them or the round-trip test breaks.

## Schema quirk

`rules.target_category` is `NOT NULL` in the spec's schema even though exclusion rules don't logically use it. Creating an exclusion rule without a category will hit an `IntegrityError` unless you default it (the API defaults to `"Others"` — see `routers/rules.py::create_rule`).

## Design deviations from `docs/technical-spec.md` (intentional, not oversights)

- **Staging is in-memory** (`engine/staging_store.py`), not a DB table — the spec's schema has none, and pre-commit review is inherently transient. A batch is lost if the server restarts before commit.
- **Refund pairing is not amount-only.** The literal SQL in the spec (`t1.amount = -t2.amount`) would mass-false-positive on any two unrelated transactions of equal-and-opposite amount. Pairing also requires merchant-name similarity after stripping suffix tokens like REFUND/REVERSAL (see `engine/refunds.py`).
- **`categories` table exists but isn't in the spec's schema** — added purely so the mockup's fixed category list is extensible later without a migration.

## Design decisions worth knowing (these used to live in the README)

- **Categorization precedence is a fixed sequence, first match wins**: user rules (by priority) → the card-bill-payment heuristic → contact-identifier matches → the built-in merchant/keyword word bank → a PayNow-marker fallback that flags for manual review rather than guessing. Default rules are seeded at a priority number far below anything a user would create by hand, so the built-in bank can never silently override a user's own rule.
- **The default rule bank is reconciled on every startup, not seeded once.** `migrations.reconcile_default_rules()` does `DELETE FROM rules WHERE is_default = 1` and re-inserts the whole source list. The original seed-once behaviour meant a rule added to the codebase in a later version never reached an already-existing database. Consequence: never hand-edit an `is_default = 1` row, it won't survive a restart.
- **A card bill payment has two halves, and they're gated differently.** `engine/card_payments.py` detects both. The *bank-side* outflow (`looks_like_card_bill_payment()`) is excluded only when a credit card account is actually known — already committed, or parsed earlier in the same multi-file upload; with no card statement ever uploaded that GIRO payment stays a real, visible outflow, since it may be the only record of the money leaving. The *card-side* credit (`looks_like_payment_received_on_card()`) needs no such gate: it only fires for an inflow posting to a card account, and a payment credit there is settling that card by definition — there is no reading under which it is income. Its marker list is deliberately narrower than the bank-side one, because a card statement's other credits (refunds, reversals, cashback, rebates) are real money coming back and must keep their categories. Both are code in the categorization engine rather than data-driven default rules, because a static text pattern can't express the cross-account context either one depends on.
- The card-side half was missing until the demo dataset grew to a year and made it visible: every `PAYMT THRU...` credit counted as inflow, so twelve months of card statements reported twelve bill payments as income (~$3.2k against $46k). Outflow was never double-counted — only the income side was wrong — which is exactly why it survived so long in a small dataset.
- **Schema migrations are column-existence checks, not a version-gated runner.** `PRAGMA user_version` is bumped for humans reading the schema history, but nothing branches on its value — each migration checks whether its own column exists before adding it (`_add_column_if_missing`), so re-running the whole migration set against an up-to-date DB is always a safe no-op. Fine for a schema that only grows additively; don't add a migration that needs ordering or data rewriting without revisiting this.
- **AI categorization is a background job, never inline in the upload request.** The upload/recategorize response returns immediately and the AI pass updates an `ai_status` field the frontend polls, so a slow or unreachable model can't hold the review screen hostage (and closing the dialog doesn't cancel the job). The call itself has **no timeout** on purpose — a large batch against a local model can legitimately run long, and an arbitrary cutoff silently falling back to rules-only is worse than showing progress; the review dialog surfaces elapsed time and a best-effort Terminate button after 15s instead.
- **All three AI providers call with `temperature: 0`.** Categorization is classification, not generation. The live eval harness (`backend/scripts/eval_ai_categorization.py`) against a local model showed the default nonzero sampling temperature was a bigger source of wrong answers than the prompt wording — don't "tune" it back up.

## Packaging (`backend/packaging/`, `app/desktop.py`, `app/webui.py`)

- **A packaged build is one process on one port; dev is two on two.** `app/webui.py` mounts the compiled frontend on the same FastAPI app as the API, but only when a build exists (`find_webui_dir()` returns `None` otherwise, which is the normal dev case - Vite serves the UI and proxies `/api`). The mount happens *after* every router in `main.py` because the SPA fallback is a catch-all; anything registered later is unreachable.
- **The SPA fallback must 404 on an unmatched `/api/...` path**, not return `index.html` - otherwise a typo'd endpoint reaches the client as an unreadable JSON-parse error instead of a 404. `tests/test_webui_serving.py` pins that, along with deep-link refreshes (`/rules` must serve the shell) and path traversal.
- **PyInstaller can't cross-compile** - it freezes the interpreter it runs under - so each OS's artifact is built on its own runner in `.github/workflows/desktop-build.yml`. That workflow also smoke-starts each binary and curls `/api/health` and `/`, because the failure mode that matters (a missing hidden import or data file) only appears at runtime, not at build time.
- **Three things must be told to PyInstaller by hand** (see the spec): the compiled `frontend/dist` as `webui/`, `app/schema.sql` (read via `importlib.resources`, so static analysis never sees it), and `collect_submodules("uvicorn")` - uvicorn imports its loop/protocol/lifespan implementations by string at runtime. `pdfminer`'s character-map data comes along via `collect_data_files`; without it pdfplumber raises on the first CJK-ish glyph in a statement.
- The default port is **8123**, not 8000/5173: a packaged copy runs on machines that may have anything on the usual dev ports, and `choose_port()` walks a few neighbours before falling back to an ephemeral port so a busy machine can still start the app.
- The console window is deliberate on every platform, Windows included - it's the app's only status display ("open at http://...", "closing this window shuts the app down") and the way to quit.

## Dev workflow gotchas (Windows / this environment)

- **`pkill -f "uvicorn app.main:app"` does not reliably kill a `uv run`-wrapped server on Windows/Git Bash** — `uv run` spawns a child process with a different command line, so the pattern doesn't match and the old server keeps holding the port. Symptom: a fresh `--reload` server logs `[WinError 10013] An attempt was made to access a socket in a way forbidden by its access permissions` and silently fails to bind, while the *old* process keeps serving stale code. Find the real PID with `netstat -ano | grep ":8000" | grep LISTENING` and kill it with `powershell -Command "Stop-Process -Id <PID> -Force"`.
- **DB path env vars behave differently.** `SG_TRACKER_DB_PATH` is re-read on every call (safe to set per-test). `SG_TRACKER_HOME` is only read once at import time to compute `CONFIG_DIR` — setting it after the process has started does nothing. Use `SG_TRACKER_DB_PATH` for test isolation; only use `SG_TRACKER_HOME` when specifically testing the config.json-driven relocate flow, and set it before the process starts.
- **`uv_build` needs explicit module-name config** for a `src/app` layout that doesn't match the project name: `[tool.uv.build-backend] module-name = "app"` in `pyproject.toml`. Without it, `uv init`'s default (`src/expenditure_tracker`) is what gets built.
- This project's installed FastAPI version wraps included routers in an internal `_IncludedRouter` — iterating `app.routes` won't show flattened sub-routes for introspection/debugging. Verify routes actually work by hitting them (TestClient or curl), not by inspecting `app.routes`.

## Browser-automation testing gotchas (claude-in-chrome)

- The `form_input` tool setting a checkbox's value **does not reliably fire React's synthetic `onChange`** — state silently stays stale even though the tool reports success. Use a real `computer` mouse click on checkboxes when testing React-controlled inputs; `form_input` is fine for `<select>` and text inputs.
- Native HTML5 `draggable`/`ondragstart`/`ondrop` (used for rule priority reordering) isn't triggered by the `left_click_drag` action — it needs real DOM drag events a synthetic mouse drag doesn't produce. Verify drag-and-drop-backed features via a direct API call instead of trying to simulate the drag in-browser.
- **A dev session can "verify" a UI as working when it's actually broken, because Tailwind's dev output only ever adds classes, never removes stale ones, across HMR.** See the Tailwind gotcha below — a bug in a dynamically-built class name silently had zero backing CSS for an entire session's worth of live-browser testing, because an *older*, literal version of the same string happened to already be compiled in from before a refactor. It only surfaced after the dev server restarted. If a layout-affecting change touches how a className string gets built (not just its content), a `Ctrl+C`/restart of the dev server before the next live check is cheap insurance a hot-reloaded session can't give you.

## Frontend gotchas

- **A Tailwind arbitrary-value class (`grid-cols-[...]`, `w-[...]`, etc.) built at *runtime* from a template literal has no CSS behind it, even though it renders in the DOM with no error.** Tailwind's scanner is purely static: it only generates a rule for an arbitrary-value class that appears as a complete, literal substring somewhere in the source text it scans. A class assembled from an array/variable (`` `grid-cols-[${columns.map(c => c.width).join('_')}]` `` — this was `DataTable.tsx`'s original `dataTableGridClass()`) never matches, no matter how "valid" the resulting string looks, because Tailwind never evaluates JS - it only reads bytes. The failure mode is silent and easy to miss in dev: Tailwind's dev-mode CSS output is additive across HMR, so if an *older*, literal version of that exact string was ever scanned before (e.g. before the value got extracted into a shared helper), the generated rule stays in the stylesheet for the life of that dev-server process even after the source no longer contains any literal producing it — the bug only surfaces on a full dev-server restart or a real `npm run build` (both scan from a clean slate). Symptom when it does surface: every column of a `display: grid` container collapses into one implicit column (each child full-width, stacked), since `grid-template-columns` silently has no value. Fix for anything computed at runtime: set it as an inline style (`style={{ gridTemplateColumns: template }}`) instead of building a class name — a DOM property has no scanning requirement. `DataTable.tsx`'s `dataTableGridTemplate()` now returns a bare value string for exactly this reason; a genuinely static, hand-typed `grid-cols-[...]` class (never built from a variable) is fine.
- **A `position: sticky` element with no explicit `z-index` will get painted over by any later DOM sibling that scrolls into the same screen region.** Stickiness alone doesn't grant stacking priority — an element with `position: sticky` and no `z-index` has stacking level `auto`, which paints in plain DOM-order like static content. If a sticky header sits above rows/content that includes anything with its own visual weight (an icon, a colored banner, a shimmer placeholder), give the header an explicit `z-10` (see `ReviewDialog.tsx`'s column header and `Dashboard.tsx`'s feed header, both `sticky top-0 z-10`) rather than assuming "sticky" already implies "on top."
