# Notes for Claude Code

Non-obvious stuff learned while building this. Don't re-derive these the hard way.

## UOB PDF parsing (`backend/src/app/parsing/uob/`)

- These statements have **no table gridlines** — columns are pure whitespace alignment. Don't reach for `pdfplumber.extract_table()`; it needs ruling lines. Instead: cluster words into physical lines by `top` proximity (`pdf_utils.group_into_lines`), then bucket each line's words into columns by hardcoded x-ranges calibrated against the real samples (see `pdf_utils.Column`).
- **Every page has a bilingual disclaimer footer** whose words fall inside the description column's x-range (e.g. "UOB Plaza Singapore" lands at x0≈128, inside the 100–330 description bucket). If you don't filter words by `top < FOOTER_TOP_CUTOFF` (780) *before* grouping into lines, footer text silently gets appended to whatever transaction was last on the page. This was a real bug — caught it by grepping parsed output for `"relation thereto"`.
- **Card statement `SUB TOTAL` is a running balance, not this statement's net.** It equals `PREVIOUS BALANCE + charges − credits`, not `charges − credits` alone. If you're cross-validating a parser against the printed total, you must include `PREVIOUS BALANCE` in the formula or every multi-month sample will look "wrong" when it isn't.
- **Card identity line vs. Summary table is a real false-positive trap.** The per-card `Summary` table near the top of page 1 also contains the card number as its own word — a naive "any line matching the card-number regex is the identity line" grabs the Summary row (wrong card name) instead of the true per-card identity line right above the transaction table. Fix: only resolve identity by searching *backward* from a confirmed `Post`/`Trans` header line, never by scanning forward for the number pattern.
- Account statement dates have no year (`"05 May"`) — derived from the `Period: ... to ...` line. Card statement dates have no year either (`"10 JUN"`) — derived from `Statement Date`, with `year -= 1` when a transaction's month is later than the statement's month (Dec/Jan wraparound).
- `BALANCE B/F`, `Total` (account statements) and `PREVIOUS BALANCE`, `SUB TOTAL`, `TOTAL BALANCE FOR ...` (card statements) are not transactions — they're excluded by exact-prefix text match, not by column heuristics.

## Which banks are supported is data, not copy (`parsing/base.py`)

- **`BankParser.parsing_implemented` is the single source of truth for "does this bank work yet".** All three Singapore banks parse now, so `detected_banks` is empty — but the flag stays, because the next bank someone stubs needs it. `GET /api/settings` splits the two into `supported_banks` / `detected_banks`, and the UI reads those: the dashboard's first-run empty state (`bankListLabel` in `Dashboard.tsx`) and the Settings → Region card. The empty state used to hardcode "Upload a DBS, OCBC, or UOB e-statement", which at the time claimed two banks that didn't parse. Don't retype a bank list into user-facing copy — implementing a parser should flip every claim about it in one move, and implementing DBS and OCBC did exactly that with no UI edit.
- `registry.detect_and_parse`'s fallback error only names banks that can actually parse, since a detected-but-unimplemented bank raises its own more specific error before that line is ever reached. It takes an optional `parsers=` override so `tests/test_bank_support_status.py` can still exercise the stub path against a stub defined for the purpose — no real bank is one any more.

## DBS and OCBC run on a shared spec engine (`parsing/columnar.py`)

- **They started with no real statement, and OCBC still has none.** No bank publishes a specimen statement PDF (their "understanding your statement" pages are annotated screenshots). The "bank statement template" sites a search surfaces are forgery tools for faking proof of income — useless here even setting aside what they're for, since they're drawn to convince a human rather than to be structurally faithful. And [monopoly](https://github.com/benjamin-awd/monopoly), which parses 18 institutions and is the most complete Singapore parser going, keeps its own test statements **git-crypt encrypted** in its repo: the person best placed to share one can't. What *is* public is the layout — column headings, row furniture, date formats — recoverable from open-source parser configs and their (unencrypted) extracted-output fixtures. **DBS was later rebuilt against two real consolidated statements** (see the next section); OCBC is still layout-only, so don't assume its spec reflects reality.
- **So DBS/OCBC are declarative `TableSpec`s over a shared engine, not two more hand-tuned copies of the UOB code.** UOB stays hand-written: its column x-ranges were measured off real statements, and porting it onto the engine with nothing to re-validate against would trade tested code for untested code. Don't "unify" them.
- **Column ranges are derived from the header row at parse time** (`pdf_utils.columns_from_header`), not hardcoded. Boundary rule depends on the column to the *right* of it (`_left_bound`): before a **right-aligned** column (an amount) the divider is that column's own header left edge — an amount right-aligned under "WITHDRAWAL" never starts before the "W", while the left-aligned description beside it legitimately runs past the midpoint of the header gap, so anchoring on the header's left edge is what stops "... PTE LTD" being read as a withdrawal. Before a **left-aligned** column the divider is the *midpoint of the empty gap* between the two header words: a real DBS row's "Advice ..." description begins at the exact same x as the "Description" header, and floating-point equality is not a boundary to bet a parse on. The first fixture run used the header's left edge for every boundary and dropped the first description word of every DBS row into the date column.
- **Every parse ends in `_reconcile` against a figure the statement prints for itself**, and raises rather than returning. This is deliberate and load-bearing: a spec that has drifted from a bank's real layout fails by having a column boundary land a few points off, which produces a *plausible* import with wrong numbers. That is worse than a refused one. The check caught three genuine bugs during initial development and confirmed the real-DBS rebuild.
- **A page can carry more than one table.** DBS's consolidated eStatement — its default — prints every account you hold as consecutive sections, often several to a page. The UOB layout never did this, so `parse_table` reading only the first header per page went unnoticed until the consolidated fixture landed; it poured the second account's rows into the first. Section boundaries stop at the *next section's heading*, not its table header, because the account name/number/currency lines between them carry no date and would otherwise be appended to the previous section's last transaction.
- **A section with no transactions is dropped** (`parse_table`), and `parse_table` raises if that leaves none. A real DBS consolidated statement lists a dormant SRS account as a heading over an empty table; emitting a transaction-less `ParsedAccount` for it would just be downstream clutter.
- **`extract_words` carries `upright`, and the engine drops non-upright words** before grouping into lines. A real DBS consolidated statement prints its legal-entity block ("DBS Co. Reg. No. 196800306E", the POSB Biz Reg No.) as a **rotated vertical strip down the left margin at x≈11**; pdfplumber reads each fragment with a `top` that collides with a transaction row's, so without the filter they merge into the row text ("BSOP YUPEI", a reversed reg number glued onto a transaction line). UOB's parsers don't use this filter — their footer trap is horizontal and handled by `footer_top_cutoff`.

## What the real DBS consolidated statements taught (`parsing/dbs/`)

- **Transaction rows print the year in full** ("01/12/2023"), unlike UOB/OCBC's year-less "01 OCT". `columnar.parse_row_date` returns `(day, month, year|None)`; a `None` year means resolve from the statement date (`YearResolver`), a real year is used as-is. The synthetic DBS fixtures were regenerated to `DD/MM/YYYY` to match.
- **The reconcile row is `Total Balance Carried Forward in SGD: <withdrawals> <deposits> <balance>`** — one row carrying all three figures, at the end of the section. The per-page `Balance Brought Forward SGD <n>` / `Balance Carried Forward SGD <n>` rows are page furniture, *not* the section total — `closing_balance_prefix` and `totals_prefix` are both `"Total Balance Carried Forward"` for exactly this reason. An earlier guess that "Balance Carried Forward" was the closing-balance row captured the last *page's* carried-forward and mismatched the real final balance by whatever the last page added.
- **Detection can't rely on "DBS Bank".** A real consolidated statement never prints it on the cover (bank identity is the "PDS_MMCON..." footer doc code and the reversed vertical strip), and a sanitized sample keeps only parser-relevant words. `DBSParser.detect` matches "DBS Bank" / "POSB" / "PDS_MMCON", else `"DBS"` plus a furniture row DBS phrases its own way ("Balance Brought/Carried Forward", where UOB and OCBC say "BALANCE B/F").
- **The statements are encrypted with an empty user password** (owner-locked against editing, readable with no password). `pdf_io.open_pdf` tries `decrypt("")` before raising `EncryptedPdfError`, so these upload without the app demanding a password that doesn't exist.
- **The identity heading is one line**: "DBS Multiplier Account Account No. 120-752744-8". `_account_identity` strips a trailing "Account No." label (`LABEL_SUFFIX_RE`) to leave just the account type. The synthetic fixture used to split it across two lines; it now matches the real single-line form.

## The DBS/OCBC sample fixtures are now two kinds (`PDF Examples (Sanitized)/`)

- **`DBS/Account Statements/SampleConsolidatedStatement_{Dec2023,Nov2024}.pdf` are sanitized from real statements** — `scripts/sanitize_statement.py` with `--keep multiplier --redact JUN` (JUN is a real counterparty-name syllable that collides with the month abbreviation in the sanitizer's vocabulary). They prove the parser reads the layout DBS actually prints, and `test_dbs_real_consolidated_statement_parses_and_reconciles` pins their counts and reconciled totals.
- **Everything else in `{DBS,OCBC}/` is synthetic** (`scripts/generate_dbs_ocbc_samples.py`). The DBS half was updated to the real layout; OCBC's is still layout-only and *cannot validate the layout, only the parser* — if the OCBC layout understanding is wrong, fixture and parser are wrong together.

## The statement sanitizer (`app/sanitize.py`, CLI at `scripts/sanitize_statement.py`)

- **The rules live in `app/sanitize.py`; the script is a thin CLI over it.** They started in the script, and the move was forced by packaging: `packaging/spend-track.spec` bundles `backend/src/app` and three named data files, and nothing under `backend/scripts/`, so a packaged desktop build could not reach the sanitizer at all. Consequence to remember: **`reportlab` is a runtime dependency now, not a dev one.** No spec change was needed for it - `pyinstaller-hooks-contrib` already ships `hook-reportlab.pdfbase._fontdata.py` and `hook-reportlab.lib.utils.py`, and adding `collect_data_files("reportlab")` would duplicate a maintained hook. What guards it instead is a `curl -F` against `/api/contribute/sanitize` in `desktop-build.yml`'s smoke block, because a missing bundle only fails at runtime.
- **The CLI's contract is bytes-in from the module, Paths and exits of its own.** `read_pages` raises `EncryptedPdfError`/`IncorrectPasswordError` and the CLI translates them into `SystemExit`; the module must never raise `SystemExit` itself, because it is a `BaseException` and, raised in FastAPI's threadpool, it propagates past Starlette's exception middleware and escapes into the test runner. `test_no_system_exit_can_escape_the_sanitize_module` pins that structurally. The `sys.path.insert` for `src` still exists but is now one line in the CLI's import preamble, run once - `test_runs_as_a_script_from_a_clone` runs the script by absolute path with nothing installed, so it cannot go away.
- **`render_pdf` passes `invariant=1`, and that is a privacy fix, not a determinism nicety.** Without it reportlab stamps `/CreationDate (D:20260903202532+08'00')` into every output: the author's wall clock and their timezone, correlating with whenever they posted the issue. Every sanitized sample this project shipped before had it. It also makes output byte-identical run to run, which `test_the_output_carries_no_timestamp_or_timezone` leans on.
- **`verify` strips `EDGE_PUNCTUATION` from a token before looking it up in `written`.** A word's boundaries do not survive the round trip: punctuation passes through `redact_line` verbatim (no alphanumeric character to replace), `render_pdf` draws no space between two words whose boxes touch, and the pair re-reads as one token. Every real DBS statement hit this on the footer URL, reporting `xxxx://xx.xxx.xxx/xx-xxxxxxxxxx.` as a leak in a file where nothing had leaked. A verifier that cries wolf is worse than no verifier, because the one time it is right is the time it gets ignored. Only the edges are forgiven, so no alphanumeric character can ride in on it - `test_the_verifier_still_refuses_a_replacement_with_real_text_attached` pins that half.
- **A PDF with no extractable text sanitizes to a blank page that passes every check.** Verification is exhaustive over *survivors*, so zero survivors is vacuously clean: the CLI exits 0 on a scan and writes a 1.4 KB file of nothing. `SanitizeResult.word_count` exists to catch it, and the Contribute endpoint withholds the file entirely in that case. It is not a `problems` entry - nothing leaked, it is the wrong kind of file.
- **`ParseCheck.detail` may quote the contributor's real figures.** `StatementReconciliationError` subclasses `UnparseableStatementError`, so a failed parse can read "the statement prints total withdrawals of 12,480.55 but the transactions sum to 9,930.55". It is screen-only: never in the GitHub issue prefill, never behind a copy button, and `account_summaries` is built from parser output rather than from an exception precisely so there is something safe to send.
- **It is default-deny, and that is what makes it small.** A word survives only if it is positively recognized as the bank's template (`CHROME_VOCABULARY`), a date, or a figure; everything else is replaced with its shape. An earlier version worked the other way round - spot the personal words, keep the rest - and needed rules for NRIC, emails, phone numbers, counterparty names after `To:`/`From:`/honorifics, split digit runs, plus a name-candidate review list and a whole-document cross-check to manage what those rules inevitably missed. Inverting the default made every one of those redundant and cut the script roughly in half. Don't reintroduce a "looks personal" rule; widen the vocabulary instead.
- **The merchant rule bank and shared statements are independent contributions, in both directions.** `engine/default_rules.py` is merchant strings and categories - it needs no statement, and there is an issue template (`merchant-rules.yml`) for contributing it as plain data. That decoupling is what makes the sanitizer viable at all: because a parser passes descriptions through untouched, a shared statement can discard every one of them without costing a parser author anything. Don't reintroduce "this sample can't test categorization" as a caveat on the sanitizer - the sample was never the way to get those rules.
- **The premise is measured, not assumed: a parser never reads a description.** It keys on the bank name, the column headings, the B/F and Total rows and the statement date, then uses geometry for the rest. `test_sanitizing_costs_the_parsers_nothing` runs the sanitizer over every committed fixture and asserts identical dates, amounts and balances - if a parser ever grows a dependency on customer wording, that test says so. Geometry *alone* is not enough, though: strip the chrome too and no parser can even identify the bank.
- **It rebuilds the PDF; it never edits one.** Drawing a black box over text leaves the text in the content stream - that is how real redaction failures happen. Reading every word's geometry and drawing a fresh document means the original text, images, annotations, metadata and any earlier incremental-save revision are absent by construction rather than by removal.
- **Each word is drawn horizontally scaled into the original's exact bounding box** (`_draw_fitted`). Preserving x0/x1 matters more than the glyphs rendering at their natural width, because column bucketing keys off exactly those two numbers.
- **Space glyphs have to be drawn back in between words.** This is non-obvious and it broke the first working version completely. pdfplumber splits a line into words at whitespace *characters* first, falling back to a 3pt gap threshold only otherwise - and real inter-word gaps are routinely under 3pt, because the source PDF had an actual space character doing the splitting. Drawing each word on its own removes those spaces, so the output re-reads as one giant token per line and parses as nothing at all.
- **`_shape_of` only maps letters, so digits must be pseudonymised first.** A reference like `PIB0000123456789012` otherwise comes out as `XXX0000123456789012` - the whole thing intact behind a masked prefix.
- **`is_year` exists because there is no length threshold.** A bare four-digit year is a digit run with no separators; unguarded, it went through the pseudonymiser and moved every transaction to the year 6557, silently, since the dates still looked like dates. Bounded to 1900-2099 so a four-digit card group still goes.
- **Verification is exhaustive rather than heuristic**, which is the other thing default-deny buys: every word in a finished file must be template, a date, a figure, something `--keep` named, or text the script itself wrote. `written` is passed in because a replaced *number* is indistinguishable by inspection from one that survived - both are digit strings - but the words are still looked for in the finished file, so it stays a check on the artifact rather than on the model.
- **The file name is part of the leak surface.** `JaneWong-Jan2024.pdf` identifies its owner as well as its contents do, and it's what gets attached to an issue. Checked against the *output* name, not the input's, or passing `--output` couldn't fix it.
- **`--redact` covers the one case default-deny cannot**: a name that *is* a template word (someone called May, a merchant called Trust). It matches whole words joined end to end, never substrings - substring matching would make `--redact "JANE TAN"` strike every `STANDARD CHARTERED`, and over-redaction is not free, since what survives is the entire reason to share the file.
- **The console output must never read as an all-clear**, and there's a test asserting it doesn't contain "no PII" / "safe to share" / "all clear". An earlier version printed "verified: no NRIC, email, or --redact text found" over five real names sitting in the output.

## The Contribute page (`routers/contribute.py`, `pages/Contribute.tsx`)

- **`POST /api/contribute/sanitize` holds nothing between calls, and that is a privacy decision rather than a simplicity one.** The obvious optimization is caching the parsed pages so striking one more word off the list does not re-read the PDF - but those pages are the *un-redacted* `Word` list, every name and account number, held in process memory for as long as a contributor keeps the tab open. Recomputing from the re-posted bytes is the cheaper risk. The frontend re-posts an `ArrayBuffer` read once, not the `File`, because a `File` from an `<input>` is a live disk handle Chrome invalidates if the file moves and a chip-editing session lasts minutes.
- **It is `def`, not `async def`,** so FastAPI runs the pdfplumber and reportlab work in its threadpool. `test_the_endpoint_runs_off_the_event_loop` pins it against a future "modernize to async" edit, and `test_the_sanitizer_is_imported_from_main` pins the top-level import, which is the actual property that makes PyInstaller bundle the module.
- **Verification failure warns and still hands over the file; a scan withholds it.** Two different answers, and the split lives in the *router*, never in `sanitize()` - the CLI deliberately writes the file it refuses so a maintainer can see what leaked, and `test_the_cli_still_writes_the_file_it_refuses` stops that getting "tidied up" into the shared orchestrator.
- **The uploaded filename never appears in a response.** `JaneWong-Jan2024.pdf` identifies its owner as well as the contents do. `suggested_filename` is the typed bank slug plus a hash of the input bytes, and it is fed back to `verify` as `output_name` so the existing "the file name contains a word you asked to remove" check fires on the name the browser will actually save. Do not copy `statements.py`'s idiom of echoing `f.filename` into an error message here; `test_nothing_from_the_uploaded_filename_reaches_the_response` greps the whole body.
- **The chip list cannot be exhaustive and the copy must not pretend otherwise.** `kept_words` filters on `any(c.isalpha())`, so amounts, dates and short numbers are kept and never listed. "Do you see your street?" over a list that cannot hold a street number is a promise the engine does not keep - the preview iframe is what discharges "see what you are sharing", and `surviving_oddities` (surviving tokens with no letter that are not money or a date) is the short list where a stray identifier would actually hide.
- **Only the typed bank and closed-set facts go in the GitHub prefill URL.** It is the one thing in this feature that leaves the machine, and the omnibox, history and any proxy see it before the user reads the form. Never `kept_words`, never the filename, never `parse_detail`.
- **The page suspends the app-wide drop handler while mounted** (`UploadProvider`'s `setGlobalDropSuspended`). Without it, dropping a statement on Contribute would start a real import into the user's own history. The window listeners keep calling `preventDefault` while suspended - they just stop claiming the file - because otherwise the browser navigates the tab to the dropped PDF.

## Sanitized sample PDFs (`backend/scripts/generate_sample_pdfs.py`, `generate_dbs_ocbc_samples.py`)

- Two generators, sharing only `scripts/statement_canvas.py` (the pdfplumber-`top`-to-reportlab-`y` conversion and the per-page footer). `generate_sample_pdfs.py` is UOB and draws at hand-measured x-positions; `generate_dbs_ocbc_samples.py` draws at plausible-but-arbitrary ones, since the DBS/OCBC parsers read their columns off the header row anyway. The DBS/OCBC generator wraps long descriptions by *measured* text width against the boundary the parser will derive, so the fixtures can't quietly overflow a column the way a guessed character count would let them.


- **Jan-Jun are pinned regression fixtures; Jul-Dec are the demo dataset.** The first six months are written out longhand in the generator and their totals/counts are asserted by name in `tests/test_sanitized_sample_parsers.py` - changing them breaks tests on purpose. The Jul-Dec months are built from row helpers (`nets`/`direct`/`paynow_out`/`salary`/`card_bill`/...) and exist so uploading the whole folder fills every chart in the UI; they're what `docs/screenshots/` is shot from. Two parameterized tests walk *whatever* is in the folder (each account statement reconciles against its own printed `Total` row, each card statement yields cards with transactions), so a month added later is covered the day it lands.
- `PDF Examples/` is an optional, gitignored local folder for testing against your own real statements - a fresh clone has none, and the tests that use it (`test_uob_account_parser.py`/`test_uob_card_parser.py`/`test_registry_and_pdf_io.py`/`test_statements_router.py`/`test_crud_routers.py`) discover files in it by glob and skip gracefully when it's absent, rather than hardcoding a filename. `PDF Examples (Sanitized)/` is synthetic and committed; `tests/test_sanitized_sample_parsers.py` runs against it unconditionally so `uv run pytest` always exercises the parsers even without real statements.
- The generator draws text with `reportlab.pdfgen.canvas` at the **exact same column x-positions** the parser's `Column` definitions expect (kept in sync manually - there's a comment pointing back at each parser file). That's what makes the output round-trip through the real parser correctly; it's not just a lookalike, it's parseable.
- Coordinate systems differ: pdfplumber's `top` is distance-from-page-top (what the parser's column ranges are calibrated against), reportlab's `y` is distance-from-page-bottom, ascending. The conversion used is `y = PAGE_H - top - font_size * 0.8` (approximates baseline offset) - exact pixel alignment doesn't matter, only that words on the same logical row land within 3pt of each other (the parser's line-grouping tolerance) and each column's x falls inside the right bucket.
- The multi-card statement fixture (`SampleCardStatement_MultiCard_Mar2024.pdf`) exercises a code path **no real sample ever covered** - two cards in one statement - and is what caught that the identity-line-vs-Summary-table backward-search fix actually works for a genuine multi-card case, not just the single-card real samples.
- `scripts/seed_demo_data.py` rebuilds the screenshot database from those PDFs (contacts and rules first - categorization runs at upload time, so a contact created afterwards owns nothing and reads $0 spend). Re-shoot `docs/screenshots/` from it at 1440x750 @2x, which is the 2880x1500 the committed images already use.
- Regenerate with `uv run python scripts/generate_sample_pdfs.py` (`reportlab` is a runtime dependency now - see the sanitizer section). If you change a parser's column x-ranges, the generator's constants (`ACC_*`/`CARD_*` at the top of the script) need to move with them or the round-trip test breaks.

## Adding a category to `DEFAULT_CATEGORIES` (`migrations.py`)

- **It needs no migration, but it does need an icon on the frontend.** `reconcile_categories` upserts the whole list on every startup, so a new entry reaches every existing database - but `lib/categoryColor.ts`'s `ICON_COMPONENTS` is a hand-maintained string-to-lucide map, and an icon name missing from it silently falls back to a generic `Tag`. Add both halves in the same change (Travel = `plane`).
- **The hue wheel is nearly full, and two of its widest gaps are spoken for.** The category hues plus `index.css`'s semantic tokens (warning 70, review 250, ai 285, danger 25, success 150) leave only ~30-degree gaps at 205 and 45. Both put a new category 15 degrees from each neighbour; pick on which neighbours it's worse to be confusable with. Don't take 70 or 250 - the needs-review token was moved off amber precisely because it sat next to a category hue.
- **A user may already have created a category by that name.** The upsert is keyed on `name`, so theirs is adopted (hue/icon/sort_order/direction overwritten) rather than duplicated - `tests/test_crud_routers.py` pins that. One sharp edge: if they had created it as an *inflow* category and it becomes an outflow default, `_migrate_direction_mismatched_transactions` moves their inflow rows in it to "Other Income" on the next startup. Inherent to adding any default category, not to any particular one, but worth knowing before picking a name people plausibly use.

## The default rule bank's short patterns (`engine/default_rules.py`)

- **A rule matches by plain case-insensitive substring** (`engine/rules.py`: `rule["match_pattern"].upper() in desc_upper`), so a short pattern is only safe if its *shape* makes it safe. Two entries rely on a trailing space for that: `"CHEERS "` and `"GV "`. Neither brand's own name appears on a statement - Golden Village prints as `GV PLAZA SINGAPURA`, Cheers as `CHEERS - STEVENS MRT` - and without the space they would fire inside longer words (`CHEERSFUL HOLDINGS`, anything containing `...GV...`). `tests/test_default_rules.py` pins both directions.
- `iter_default_rules()` sorts longest-pattern-first, so a short pattern only ever gets a turn after every more specific one has missed. That is what makes adding one low-risk - but it is not a substitute for the trailing space, which is what stops a *mid-word* match.
- **Skip anything that could be a person.** UOB's NETS lines truncate the merchant and glue a terminal ID on (`THRIVE FOOD18399883`), and some of those truncations read as names. The bank is public and shared; a business name is fine, a person's is not, and an ambiguous one is not worth the rule.

## Opening a folder in the OS file manager (`routers/data_lifecycle.py::reveal_database`)

- **It is the only endpoint in the app that shells out, and it takes no path.** The argv is built from `get_db_path()` alone, as a list (never a shell string), so there is nothing user-supplied anywhere near it. Don't add a path parameter "for flexibility" - that is the whole reason this is safe.
- **It returns `{opened: false, error}` instead of raising.** A container or server-hosted copy has no desktop session and no `xdg-open`; that is a legitimate answer, not a 500. Settings already prints the path, so the fallback is "open it yourself".
- macOS and Windows select the file (`open -R`, `explorer /select,<path>` - no space after the comma); everything else opens the parent directory via `xdg-open`, which has no select verb. `subprocess.Popen`, not `run`: `explorer.exe` exits non-zero even on success.

## Schema quirk

`rules.target_category` is `NOT NULL` in the spec's schema even though exclusion rules don't logically use it. Creating an exclusion rule without a category will hit an `IntegrityError` unless you default it (the API defaults to `"Others"` — see `routers/rules.py::create_rule`).

## Design deviations from `docs/technical-spec.md` (intentional, not oversights)

- **Staging is in-memory** (`engine/staging_store.py`), not a DB table — the spec's schema has none, and pre-commit review is inherently transient. A batch is lost if the server restarts before commit.
- **Refund pairing is not amount-only.** The literal SQL in the spec (`t1.amount = -t2.amount`) would mass-false-positive on any two unrelated transactions of equal-and-opposite amount. Pairing also requires merchant-name similarity after stripping suffix tokens like REFUND/REVERSAL (see `engine/refunds.py`).
- **`categories` table exists but isn't in the spec's schema** — added purely so the mockup's fixed category list is extensible later without a migration.
- **`contacts.default_category` (the spec's single `NOT NULL` column) is split into `default_category_outflow`/`default_category_inflow`, both nullable.** A contact who's both paid and paid by the same PayNow identifier (a housemate splitting bills, a client who's also a supplier) needs each direction to resolve independently — the single-column version could only ever auto-categorize one direction, silently falling through to the generic fallback on the other. `migrations.py::_migrate_contacts_category_split` rebuilds an old DB's single column into the two new ones (`ALTER TABLE ... DROP COLUMN`, not just an added column, since the old one was `NOT NULL`).

## Design decisions worth knowing (these used to live in the README)

- **Categorization precedence is a fixed sequence, first match wins**: user rules (by priority) → the card-bill-payment heuristic → contact-identifier matches → the built-in merchant/keyword word bank → a PayNow-marker fallback that flags for manual review rather than guessing. Default rules are seeded at a priority number far below anything a user would create by hand, so the built-in bank can never silently override a user's own rule.
- **The default rule bank is reconciled on every startup, not seeded once.** `migrations.reconcile_default_rules()` does `DELETE FROM rules WHERE is_default = 1` and re-inserts the whole source list. The original seed-once behaviour meant a rule added to the codebase in a later version never reached an already-existing database. Consequence: never hand-edit an `is_default = 1` row, it won't survive a restart.
- **A card bill payment has two halves, and they're gated differently.** `engine/card_payments.py` detects both. The *bank-side* outflow (`looks_like_card_bill_payment()`) is excluded only when a credit card account is actually known — already committed, or parsed earlier in the same multi-file upload; with no card statement ever uploaded that GIRO payment stays a real, visible outflow, since it may be the only record of the money leaving. The *card-side* credit (`looks_like_payment_received_on_card()`) needs no such gate: it only fires for an inflow posting to a card account, and a payment credit there is settling that card by definition — there is no reading under which it is income. Its marker list is deliberately narrower than the bank-side one, because a card statement's other credits (refunds, reversals, cashback, rebates) are real money coming back and must keep their categories. Both are code in the categorization engine rather than data-driven default rules, because a static text pattern can't express the cross-account context either one depends on.
- The card-side half was missing until the demo dataset grew to a year and made it visible: every `PAYMT THRU...` credit counted as inflow, so twelve months of card statements reported twelve bill payments as income (~$3.2k against $46k). Outflow was never double-counted — only the income side was wrong — which is exactly why it survived so long in a small dataset.
- **Schema migrations are column-existence checks, not a version-gated runner.** `PRAGMA user_version` is bumped for humans reading the schema history, but nothing branches on its value — each migration checks whether its own column exists before adding it (`_add_column_if_missing`), so re-running the whole migration set against an up-to-date DB is always a safe no-op. Fine for a schema that only grows additively; don't add a migration that needs ordering or data rewriting without revisiting this.
- **AI categorization is a background job, never inline in the upload request.** The upload/recategorize response returns immediately and the AI pass updates an `ai_status` field the frontend polls, so a slow or unreachable model can't hold the review screen hostage (and closing the dialog doesn't cancel the job). The call itself has **no timeout** on purpose — a large batch against a local model can legitimately run long, and an arbitrary cutoff silently falling back to rules-only is worse than showing progress; the review dialog surfaces elapsed time and a best-effort Terminate button after 15s instead.
- **All three AI providers call with `temperature: 0`.** Categorization is classification, not generation. The live eval harness (`backend/scripts/eval_ai_categorization.py`) against a local model showed the default nonzero sampling temperature was a bigger source of wrong answers than the prompt wording — don't "tune" it back up.

## Backup export (`routers/data_lifecycle.py::export_backup`)

- **The zip's `data.db` comes from SQLite's backup API, never a file read.** SQLite writes a `-journal` sidecar mid-transaction, so copying the file off disk at the wrong moment yields a database that needs recovery — and the moment a user is most likely to click Download is right after an upload. `Connection.backup()` serializes against writers and returns something consistent by construction. `tests/test_backup_export.py` asserts `PRAGMA integrity_check` on the extracted copy plus row-count parity with the live DB.
- **API keys are stripped from the bundled `config.json`** (`config.SECRET_CONFIG_KEYS`). Everything else in it survives, so restoring costs re-entering one key rather than reconstructing the whole AI setup. A test greps the entire zip's bytes for the secret, not just the parsed JSON, so a future change that copies the config somewhere else in the archive still fails.
- **The zip carries a `README.txt` with restore steps**, because the person most likely to need it is the person who no longer has the app installed and can't read the in-app guide. It names the default folder per platform and the Change Database Path alternative.
- Built in memory (`io.BytesIO`): a year of statements is a few MB, and a temp file would need cleaning up on a path that can fail halfway.
- There is deliberately **no import/restore endpoint**. Restoring is "copy two files into a folder", which needs no code and can't corrupt a live database; an import path would need overwrite semantics, schema-version checks, and a way to fail safely mid-write.

## Packaging (`backend/packaging/`, `app/desktop.py`, `app/webui.py`)

- **A packaged build is one process on one port; dev is two on two.** `app/webui.py` mounts the compiled frontend on the same FastAPI app as the API, but only when a build exists (`find_webui_dir()` returns `None` otherwise, which is the normal dev case - Vite serves the UI and proxies `/api`). The mount happens *after* every router in `main.py` because the SPA fallback is a catch-all; anything registered later is unreachable.
- **The SPA fallback must 404 on an unmatched `/api/...` path**, not return `index.html` - otherwise a typo'd endpoint reaches the client as an unreadable JSON-parse error instead of a 404. `tests/test_webui_serving.py` pins that, along with deep-link refreshes (`/rules` must serve the shell) and path traversal.
- **PyInstaller can't cross-compile** - it freezes the interpreter it runs under - so each OS's artifact is built on its own runner in `.github/workflows/desktop-build.yml`. That workflow also smoke-starts each binary and curls `/api/health`, an asset, a deep link and a bad `/api` path, because the failure mode that matters (a missing hidden import or data file) only appears at runtime, not at build time.
- **The desktop build does not run on pull requests** - only on a `v*` tag or a manual dispatch. Nothing routinely proves a packaging change builds on Windows and macOS before it lands, so run the workflow by hand from the Actions tab after touching `packaging/`, `desktop.py` or `webui.py`. The backstop is that the `release` job needs `build`, so a break fails the release rather than shipping.
- **Three things must be told to PyInstaller by hand** (see the spec): the compiled `frontend/dist` as `webui/`, `app/schema.sql` (read via `importlib.resources`, so static analysis never sees it), and `collect_submodules("uvicorn")` - uvicorn imports its loop/protocol/lifespan implementations by string at runtime. `pdfminer`'s character-map data comes along via `collect_data_files`; without it pdfplumber raises on the first CJK-ish glyph in a statement.
- The default port is **8123**, not 8000/5173: a packaged copy runs on machines that may have anything on the usual dev ports, and `choose_port()` walks a few neighbours before falling back to an ephemeral port so a busy machine can still start the app.
- **The version lives in two places and a release names a third**: `pyproject.toml`'s `version`, the spec's `CFBundleShortVersionString` (what macOS shows in Get Info), and the `v*` tag the release is cut at. Bump all three together, or a download reports a version nobody released.
- The console window is deliberate on every platform, Windows included - it's the app's only status display ("open at http://...", "closing this window shuts the app down") and the way to quit.

## Dev workflow gotchas (Windows / this environment)

- **`pkill -f "uvicorn app.main:app"` does not reliably kill a `uv run`-wrapped server on Windows/Git Bash** — `uv run` spawns a child process with a different command line, so the pattern doesn't match and the old server keeps holding the port. Symptom: a fresh `--reload` server logs `[WinError 10013] An attempt was made to access a socket in a way forbidden by its access permissions` and silently fails to bind, while the *old* process keeps serving stale code. Find the real PID with `netstat -ano | grep ":8000" | grep LISTENING` and kill it with `powershell -Command "Stop-Process -Id <PID> -Force"`.
- **That PID can itself be a lie — and confirmed this by direct test, not just inference.** `uvicorn --reload`'s reloader spawns the actual worker as a `multiprocessing`-forked child (`python.exe -c "from multiprocessing.spawn import spawn_main; spawn_main(parent_pid=<reloader-pid>, ...)"`), and the *worker*, not the reloader, is what's actually listening. Reproduced directly against a `start-test.*` instance: `netstat -ano` and `Get-NetTCPConnection -LocalPort 8001 -State Listen` both reported the reloader's PID as the port's owner; `Stop-Process -Id <that-PID> -Force` ran with no error and `Get-Process -Id <that-PID>` afterward confirmed it was genuinely dead — **and `netstat`/`Get-NetTCPConnection` still reported port 8001 LISTENING under that same now-dead PID**, while `curl http://127.0.0.1:8001/api/health` kept succeeding the whole time, because the forked worker child was still alive and still holding the socket. Killing that worker's actual PID (found via `Get-CimInstance Win32_Process | Where-Object { $_.CommandLine -match "spawn_main" -and $_.CommandLine -match "parent_pid=<reloader-pid>" }`) is what actually freed the port - confirmed by the port dropping out of `netstat` and the health check failing with connection-refused. **The practical fallout: `netstat`/`Get-NetTCPConnection`'s LISTENING line cannot be trusted as kill-verification even when the PID it names is independently confirmed dead.** The only real verification is an active check - `curl` a known endpoint (`/api/health` for "is anything answering", `/openapi.json | grep <a route you just added>` for "is it the *new* code, not a stale still-alive worker") - never just "the reported PID no longer exists" or "Stop-Process didn't error."
- **Never hunt for the real worker PID with a bare, unscoped command-line pattern match across the whole process table** (e.g. `Get-CimInstance Win32_Process | Where-Object { $_.CommandLine -match "vite" -or $_.CommandLine -match "spawn_main" }` with no other filter) - on a machine that also has the user's *real* dev servers running (`start.ps1`/`start.sh` on 8000/5173, or any other Python `multiprocessing`/Vite process), that pattern matches all of them indiscriminately, and killing every match risks taking down work that isn't yours to touch. Always scope in two steps: (1) get the reloader/listener PID from a port-scoped query only - `netstat -ano | grep ":8001 "` or `Get-NetTCPConnection -LocalPort 8001 -State Listen`, filtered to the *specific scratch port*, never a bare process-name grep; (2) if that PID doesn't respond to a kill (per the point above, it usually won't for a `--reload` backend), find its worker by matching `parent_pid=<that-exact-reloader-PID>` in the `spawn_main` command line, not just `-match "spawn_main"` alone. The same two-step discipline applies to the frontend's `vite.js`/`node` process - resolve its PID from `Get-NetTCPConnection -LocalPort 5174`, never from a bare `-match "vite"` scan.
- **DB path env vars behave differently.** `SPENDTRACK_DB_PATH` is re-read on every call (safe to set per-test). `SPENDTRACK_HOME` is only read once at import time to compute `CONFIG_DIR` — setting it after the process has started does nothing. Use `SPENDTRACK_DB_PATH` for test isolation; only use `SPENDTRACK_HOME` when specifically testing the config.json-driven relocate flow, and set it before the process starts.
- **The app was renamed from "SG Expenditure Tracker" to SpendTrack, and both spellings of every env var still work** (`config.py::_ENV_ALIASES`, new name first). The existing tests all use the `SG_TRACKER_*` names and are left that way on purpose — they are the regression test for the aliases. Likewise `~/.sg-expenditure-tracker` keeps being used when it already exists and `~/.spendtrack` does not: renaming the brand must not move someone's database, especially since config.json can hold an absolute `db_path` pointing inside the old directory. `tests/test_config_paths.py` pins both behaviours.
- **`uv_build` needs explicit module-name config** for a `src/app` layout that doesn't match the project name: `[tool.uv.build-backend] module-name = "app"` in `pyproject.toml`. Without it, `uv init`'s default (`src/expenditure_tracker`) is what gets built.
- This project's installed FastAPI version wraps included routers in an internal `_IncludedRouter` — iterating `app.routes` won't show flattened sub-routes for introspection/debugging. Verify routes actually work by hitting them (TestClient or curl), not by inspecting `app.routes`.
- **Never drive the browser against the user's real dev instance (port 5173/8000) to click-test a change** — that's their actual transaction history. Use `scripts/start-test.ps1` (or `.sh`) instead: it starts a second backend+frontend pair on ports 8001/5174 against a scratch database at `.scratch-test/data.db` (gitignored), so it can run side-by-side with whatever the user already has open on the normal ports and never touches real data. Safe to re-run — like `start.ps1`/`start.sh`, it notices servers already up on those ports and leaves them alone; wipe the scratch DB anytime with `Remove-Item -Recurse -Force .scratch-test` (or `rm -rf .scratch-test`). Under the hood this is just `SPENDTRACK_DB_PATH` + uvicorn's own `--port` flag on the backend, and the new `VITE_DEV_PORT`/`VITE_API_PROXY_TARGET` env vars on `vite.config.ts` for the frontend (both default to the original hardcoded 5173/8000 when unset, so a plain `npm run dev` is unaffected) — reach for those directly if you need a *third* concurrent instance or non-default ports.

## Browser-automation testing gotchas (claude-in-chrome)

- The `form_input` tool setting a checkbox's value **does not reliably fire React's synthetic `onChange`** — state silently stays stale even though the tool reports success. Use a real `computer` mouse click on checkboxes when testing React-controlled inputs; `form_input` is fine for `<select>` and text inputs.
- Native HTML5 `draggable`/`ondragstart`/`ondrop` (used for rule priority reordering) isn't triggered by the `left_click_drag` action — it needs real DOM drag events a synthetic mouse drag doesn't produce. Verify drag-and-drop-backed features via a direct API call instead of trying to simulate the drag in-browser.
- **A dev session can "verify" a UI as working when it's actually broken, because Tailwind's dev output only ever adds classes, never removes stale ones, across HMR.** See the Tailwind gotcha below — a bug in a dynamically-built class name silently had zero backing CSS for an entire session's worth of live-browser testing, because an *older*, literal version of the same string happened to already be compiled in from before a refactor. It only surfaced after the dev server restarted. If a layout-affecting change touches how a className string gets built (not just its content), a `Ctrl+C`/restart of the dev server before the next live check is cheap insurance a hot-reloaded session can't give you.

## Frontend gotchas

- **A Tailwind arbitrary-value class (`grid-cols-[...]`, `w-[...]`, etc.) built at *runtime* from a template literal has no CSS behind it, even though it renders in the DOM with no error.** Tailwind's scanner is purely static: it only generates a rule for an arbitrary-value class that appears as a complete, literal substring somewhere in the source text it scans. A class assembled from an array/variable (`` `grid-cols-[${columns.map(c => c.width).join('_')}]` `` — this was `DataTable.tsx`'s original `dataTableGridClass()`) never matches, no matter how "valid" the resulting string looks, because Tailwind never evaluates JS - it only reads bytes. The failure mode is silent and easy to miss in dev: Tailwind's dev-mode CSS output is additive across HMR, so if an *older*, literal version of that exact string was ever scanned before (e.g. before the value got extracted into a shared helper), the generated rule stays in the stylesheet for the life of that dev-server process even after the source no longer contains any literal producing it — the bug only surfaces on a full dev-server restart or a real `npm run build` (both scan from a clean slate). Symptom when it does surface: every column of a `display: grid` container collapses into one implicit column (each child full-width, stacked), since `grid-template-columns` silently has no value. Fix for anything computed at runtime: set it as an inline style (`style={{ gridTemplateColumns: template }}`) instead of building a class name — a DOM property has no scanning requirement. `DataTable.tsx`'s `dataTableGridTemplate()` now returns a bare value string for exactly this reason; a genuinely static, hand-typed `grid-cols-[...]` class (never built from a variable) is fine.
- **A sticky element's drop shadow is drawn at rest too, and lands on the component below it.** A sticky header's own bottom padding is *inside* its box, so its bottom edge is flush against the next element - a `shadow-[0_4px_6px_-4px_...]` therefore paints ~6px of shadow directly onto the top of the first card even when nothing has been scrolled anywhere. It reads as the header overlapping the card, and it was live on all three of the Dashboard's page header, its feed column header and `ReviewDialog`'s row header. Gate the shadow class on `lib/useScrolledUnder.ts`, which returns `[scrolled, ref]`. That hook hands back a *callback* ref rather than taking an object ref because these headers only render after their page's first data arrives (the Dashboard shows a loading sentence first), so a `useEffect(..., [])` would find `ref.current === null` and never subscribe.
- **The app has a maximum width as well as a minimum.** `NarrowWindowNotice`'s `MIN_WIDTH` (1280) has always stated the floor; `--container-page` (1600px, `index.css`) is the ceiling, applied via `PageShell`'s `maxWidth` default plus `mx-auto`. Nothing on any screen gets denser as the window widens, so before this an uncapped column just stretched every component around unchanged content - at 2560px a metric card was 600px of empty space around one number, and the transaction feed put ~1200px between a description and its category. A component that legitimately grows must actually use the width (`CashFlowChart`'s bars are `flex-1` with a `max-w-*` cap; `CategoryDonut`'s legend rows draw a proportional bar like `RankedBarRow`) - stretching a row with nothing to fill it just strands its right-hand values.
- **A `position: sticky` element with no explicit `z-index` will get painted over by any later DOM sibling that scrolls into the same screen region.** Stickiness alone doesn't grant stacking priority — an element with `position: sticky` and no `z-index` has stacking level `auto`, which paints in plain DOM-order like static content. If a sticky header sits above rows/content that includes anything with its own visual weight (an icon, a colored banner, a shimmer placeholder), give the header an explicit `z-10` (see `ReviewDialog.tsx`'s column header and `Dashboard.tsx`'s feed header, both `sticky top-0 z-10`) rather than assuming "sticky" already implies "on top."
