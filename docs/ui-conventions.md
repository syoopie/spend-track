# UI Conventions

Living document. Grows section-by-section as `UI Review.dc.html`'s findings get fixed (see root of repo — the source review this doc is remediating). Each rule below exists because a real instance of it was found and fixed; the rule is what stops it from coming back. When a future UI review finds something new, add the fix *and* the rule here in the same change.

Unlike `docs/technical-spec.md`/`docs/ux-spec.md` (frozen pre-implementation design docs), this file is meant to be edited as the UI evolves — it's a checklist, not a historical record.

## Data tables / lists (transaction feed, review dialogs, contacts, rules)

- **A fixed-width column that holds icon+text (category badges, account names) must truncate, never wrap.** A wrapped cell is taller than its neighbours, and a scrolling list where row heights jitter is one of the most visible forms of jank an app can have. Give the cell `truncate` (or `whitespace-nowrap overflow-hidden text-ellipsis`) plus a `min-w-0` ancestor (grid/flex children don't shrink below content size by default) and a `title` attribute so the full value is still reachable. `CategoryBadge.tsx` is the canonical example — it truncates its label and always sets `title={category}`.
- **A long, unbounded list (>~200 rows) must paginate or virtualize — never render everything into one growing DOM list.** Page at 100 rows with a "Load more (N remaining)" control at the bottom; reset the page size back to 100 whenever the underlying filtered/sorted set changes (a stale larger page size can silently show more than a fresh filter should).
- **A sticky column header inside a long list needs its own bounded, independently-scrolling container** (`max-h-[Npx] overflow-y-auto` wrapping just the header + rows, with the header itself `sticky top-0`) — not a page-level `sticky top-0` on the header that requires measuring and subtracting some *other* sticky element's height. The bounded-container approach needs no JS measurement, doesn't depend on how tall a page-level header happens to render, and is proven in both `ReviewDialog.tsx`'s row list and `Dashboard.tsx`'s transaction feed. If you truly need a second sticky layer inside that same container (e.g. a month divider under the column header), measure *only* the sibling sticky element's own height via a `ref` + one-time `useEffect`, not the whole page.
- **A date-sorted list spanning multiple months should insert a sticky divider row per month** ("August 2026 · 104 transactions · $4,182 out") rather than letting identical-looking date labels repeat with nothing separating them. Only render dividers while the list is actually sorted by date — they're meaningless (and misleading) once sorted by anything else.
- **Any date shown in a list needs the year included whenever the active range spans more than one calendar year** (`fmtDate(iso, { withYear: true })`). A bare "Aug 28" is ambiguous the moment two different years are both in view.

## Categories

- **A category is always rendered as its icon plus its name, never as bare text.** Two components own that pairing: `CategoryBadge` (the colored pill, for a column in a table or list) and `CategoryLabel` (icon + name with no pill, for a picker's options or a filter chip, where a second background inside an existing surface is noise). Prose that happens to mention a category name (the review dialog's `AI suggested "…"` line, a refund drawer's metadata line) is the exception - an icon mid-sentence reads as a typo, not a label.
- **Every category `<select>` builds its options through `categoryOptionElements` (`components/CategoryOptions.tsx`)**, never by mapping the category list inline. Call it with no second argument for the full list, grouped into Outflow/Inflow blocks - correct for a rule, a contact's default, a filter, or a bulk edit over a mixed selection; pass an already direction-filtered `subset` for a per-row picker, which renders flat since a divider over one block is noise. `categoryOption(categories, name)` covers the one-off case of a value that isn't in the list any more (a renamed or deleted category still on an old transaction) - it falls back to a generic tag icon rather than rendering the one bare-text row in the panel. This existed as a helper before and the review dialog's bulk "Set category to…" picker still hand-rolled its own icon-less options for months; the fix is that there is now exactly one code path, so the next picker can't quietly grow a fifth copy.

## The app mark

- **The in-app logo is painted from the accent tokens, never fixed hex** (`components/Logo.tsx`: `fill="var(--color-accent)"` / `var(--color-accent-fg)`). The accent is user-configurable under Settings, so a hardcoded mark would be the one element on screen that ignores the user's choice. The static copies can't follow a CSS variable and carry the default pink instead — see below.
- **One design, three files, on purpose**: `frontend/src/components/Logo.tsx` (in-app, token-driven), `frontend/public/favicon.svg` (browser tab), `docs/logo.svg` (README, and the master the app icon is rasterized from). Change the geometry in one and change it in all three, or the tab icon quietly stops matching the sidebar.
- **`backend/packaging/icon.png` is a 512px render of that same SVG**, and is the only icon file the packaged build needs: PyInstaller converts it to `.ico` or `.icns` per platform via Pillow (already present as a pdfplumber dependency), so there are no per-platform binaries to keep in sync.
- Bar heights in the mark are short-tall-medium rather than a clean ascending ramp. A staircase reads as a signal-strength icon at 16px; an uneven set reads as a chart.

## Money

- **Always render the sign, never encode direction through color alone.** Use `fmtSigned` (`+$12.34` / `-$12.34`), not `fmtPlain(Math.abs(x))` colored differently. Color is a reinforcing signal, not the only channel for the single most important fact in a transaction row.
- **Use exactly two fixed colors for amounts** — `text-success` for inflow (positive), `text-text` (the default reading color) for outflow. Do not derive a continuous/interpolated color from the amount's magnitude (a retired helper, `amountIntensityColor`, did this via `oklch()` + `log1p` scaling — at low magnitudes the chroma dropped low enough that a $10 debit and a $10 credit were nearly indistinguishable). If magnitude needs its own visual signal, use `font-semibold` above a threshold (e.g. ≥50% of the max amount currently in view) — weight is legible at a glance in a way a subtle hue/chroma shift is not.
- **Every numeric figure rendered in `font-mono` gets tabular figures for free** — `index.css` sets `font-variant-numeric: tabular-nums` on the `.font-mono` utility globally. Don't reach for a per-component numeric class; just use `font-mono` on any stacked/aligned number the way the rest of the app already does.

## Filters (any page with more than one filter control)

- **Every filter a user can set must be visible on screen while it's active, not just reachable through the control that set it.** A category filter set by clicking a donut slice, with the category `<select>` scrolled out of view, silently shrinks a list with zero visible explanation. Render active filters as dismissible chips ("Category: Groceries ×", "Search: kopitiam ×") near the list they affect, with a "Clear all" once more than one is active.
- **A category that exists in both directions filters as one thing.** `categories.direction` is a hard property - a rule targeting "Paynow" must never fire on an inflow - but that split is a categorization concern, and it has no business leaking into a filter. Someone who picks "Paynow" is asking to see their PayNow activity; that the picker lists it under Outflow is an implementation detail. `lib/categoryPairs.ts` holds the pairs (`Paynow`/`Paynow Received`, `Others`/`Other Income`) and `categoryFilterMatches(filter, category)` is what the feed, the donut's selected-slice highlight, and the donut's click-to-toggle all compare with - not `===`. A category with no counterpart, including any the user creates, is unaffected. When a filter covers a pair, the active-filter chip names **both** halves, or getting inflow rows back from an outflow category reads as a bug rather than as the intent.
- **Every filter that affects a page's main content must persist across reloads (localStorage) *and* be mirrored in the URL query string**, so a filtered view is both remembered and shareable/bookmarkable. See `lib/dashboardFilters.ts` (`loadDashboardFilters`/`saveDashboardFilters`) paired with `useSearchParams` in `Dashboard.tsx`'s `persist()` — URL params win on initial load (a shared link should show what it promises), falling back to localStorage, falling back to a hardcoded default. Use `{ replace: true }` when writing search params on every keystroke/toggle so filtering doesn't spam browser history.
- **A live-filtering text search must be debounced (150ms is the standard used here)** and should search every field a user would reasonably expect a match against — not just the one or two fields that happened to be easy to add first. For the transaction feed that's label, raw description, category, account, and the formatted amount.

## Row interactivity / accessibility

- **A row that's clickable must also be keyboard-reachable and announce itself as interactive**: `role="button"`, `tabIndex={0}`, an `onKeyDown` handling `Enter`/`Space`, a `hover:` background, and a `focus-visible:outline` — not just `onClick` on a bare `div`. See the transaction feed row in `Dashboard.tsx`.
- **Any nested interactive control inside a clickable row must `e.stopPropagation()` in its own `onClick`**, or it will also trigger the row's click handler (double-fire at best, wrong action at worst — e.g. a refund-link button inside a row that opens the row's own editor when clicked).
- **A hover-only affordance (an edit pencil, etc.) should still be faintly visible at rest** (`opacity-40`, not `opacity-0`) so the row communicates it's editable before the user happens to hover it. Full opacity on `group-hover`/`group-focus-within` as before.

## Primitives and tokens (Batch 1 - root causes 01 and 02)

- **A "form action" button (Cancel/Save/Confirm/Discard in a modal or card footer) always goes through `components/Button.tsx`**, never a hand-rolled `<button className="...">`. Five near-identical padding variants (`px-4 py-2.5`, `px-5 py-2.5`, `px-4.5 py-2.5`, `px-3.5 py-2`, `px-3 py-2`) existed at ~40 call sites before this; `Button` collapses them to two sizes (`md` default, `sm`) and five variants (`primary`, `secondary`, `danger`, `danger-outline`, `ghost`). Bespoke controls that aren't really "a labelled button" - `Select`'s trigger, `Tabs`, calendar day cells, `Sidebar` nav items, icon-only affordances like a row's edit pencil - stay their own components; forcing those through `Button` would fight its variant set for no consistency win.
- **A standard text input goes through `components/Field.tsx`'s `Input`**, not the repeated `"w-full box-border px-3 py-2.5 rounded-lg border border-border bg-input text-text text-md"` string (~15 call sites before this). Pass `mono` for the handful that also hand-added `font-mono` (paths, DELETE-to-confirm fields, rule patterns, API keys). A handful of intentionally denser inputs (the review popover's compact fields, `px-2.5 py-1.5`) stay hand-rolled rather than fighting `Input`'s padding - see the note below on why overriding padding/width through `className` isn't safe.
- **Never pass a `className` override that fights a primitive's own width/padding utility** (e.g. `<Input className="w-[240px]">` when `Input` already sets `w-full`). Two Tailwind utilities targeting the same CSS property (`width`, `padding-inline`, ...) both end up in the generated stylesheet, and which one wins is decided by Tailwind's internal generation order, not by position in the `className` string - relying on "mine comes later" is not safe. `Input` instead takes an explicit `fullWidth={false}` prop that omits `w-full` entirely, so there's only ever one width utility active. Give any future primitive the same escape hatch (a boolean/variant prop) rather than trusting a className override to win a specificity tie.
- **A settings/summary card wrapper goes through `components/Card.tsx`**, not a repeated `"bg-card border border-border rounded-xl p-5"` div. Pass `padding=""` for a list container whose rows supply their own padding (`overflow-hidden` table-like lists), or `padding="p-4.5"` for the one tighter metric-card variant - both replace the whole padding class rather than layering a second one, so there's no width/padding conflict.
- **A page header (title, optional subtitle, optional leading icon, optional right-aligned actions) goes through `components/PageShell.tsx`**, matching the `px-9 pt-7 pb-15` + `text-title font-bold font-display` shape every page already converged on by convention before this, now shared instead of retyped. `Dashboard.tsx` is the one exception - its header is `sticky` with its own scroll-tinted background, a genuinely different layout, not just a restyle. `Guide.tsx` used to be a second exception purely because it wanted a leading accent-tinted icon tile the primitive couldn't express; that's an `icon?: LucideIcon` prop now, not a hand-rolled header. Prefer growing `PageShell` a prop over re-typing the header shape - a header variation that lives outside the primitive is one nobody updates when the shared shape changes.
- **A page header's icon is the same icon the sidebar uses to navigate to it**, in the same accent-tinted tile (`w-10 h-10 rounded-xl bg-accent/12`, `size={18}`): `LayoutGrid` for Dashboard, `Users` for Contacts, `SlidersHorizontal` for Rules, `ListChecks` for Default Rules, `BookOpen` for the Guide, `Settings` for Settings. A page whose header icon disagrees with its rail icon makes the two read as different destinations. `Dashboard.tsx` renders that tile by hand since its header is the sticky exception above - it's the one place the shape is duplicated, so change it alongside `PageShell` when the shape moves.
- **`maxWidth` bounds the padded container, not the text column.** `PageShell` puts `maxWidth` on the same div as `px-9`, so a page moving a hand-rolled `max-w-2xl` *inner* wrapper onto the prop loses 72px of content width unless it goes up one step (`Guide.tsx` uses `max-w-3xl` to keep the measure it had). Check the rendered width when converting a page, don't just copy the class across.
- **`EmptyState`/`ErrorState` (`components/EmptyState.tsx`) exist for the "no data" vs. "the backend is down" distinction** (root cause 04 / X-4 in the review doc). As of Batch 2 they're wired into the six places the review named - Rules, Contacts, Default Rules, the Dashboard feed, and both review dialogs (via `ReviewDialog.tsx`'s own empty-row rendering, shared by staging and recategorize) - each with an `isError`/`onRetry` branch calling the query's own `refetch()`. A *new* list screen still needs to wire these in itself; they don't apply themselves.
- **Semantic color literals never get hand-derived per component.** `index.css` defines tinted-surface tokens for each of the four recurring states - `--color-warning-*` (amber, "needs review"), `--color-ai-*` (violet), `--color-success-*` (green), `--color-danger-*` (red) - each with a `-surface`/`-surface-border` pair for banners and a `-badge-bg`/`-badge-fg` pair for pills/badges. Before this, `ReviewDialog.tsx` alone had six local `oklch()` constants, and `PendingReviewBanner`/`Rules`/`Settings`/`AiSection`/`Toast` each re-derived their own near-identical values. A category's *own* color is the one legitimate exception (`lib/categoryColor.ts` computes `oklch()` from a per-category hue) - that's inherently data-driven, not a fixed semantic state, so it can't be a static token.
- **A one-off pixel font size only gets a new token if it doesn't already match a Tailwind default.** `text-[12px]` is exactly `text-xs` - use that, no new token needed. Sizes with no default home (11px, 13px, 15px, 22px) get non-colliding custom names - `text-2xs`, `text-md`, `text-title-sm`, `text-title` - deliberately *not* named `xs`/`sm`/`base`/`lg`, so adding them can never silently reflow the ~85 call sites already using Tailwind's own default scale at their default sizes. The same logic applies to radii: `rounded-md`/`lg`/`xl`/`2xl` already matched this app's 6/8/12/16px scale at Tailwind's defaults and needed no new token; only the one true outlier (`rounded-[10px]`, homeless between `lg` and `xl`) got a new `rounded-2lg`.

## Async behavior (Batch 2 - root causes 03 and 04, X-3, X-4, DASH-1, REV-7)

- **A query whose key changes on user interaction (a filter, a date range, an account picker) must set `placeholderData: keepPreviousData`** (from `@tanstack/react-query`). Without it, TanStack Query resets `data` to `undefined` and `isLoading` to `true` on every key change, which is what caused the Dashboard's entire page to blank out on every range/account change (root cause 03 / DASH-1) - `useDashboardSummary`, `useTransactions`, and `useMonthlyTotals` in `api/hooks.ts` all set it now. The `QueryClient` in `main.tsx` also sets a global `staleTime: 30_000` so navigating back to an already-fresh screen doesn't refetch-and-flash either; that's a separate, complementary fix - `staleTime` does nothing for the query-key-changed case, only `keepPreviousData` does.
- **Distinguish "nothing to show yet" from "still updating."** With `keepPreviousData` in place, `query.isLoading` only stays true on the true first-ever load (nothing cached, nothing to render) - keep that as a real loading gate, but drive any "this is refreshing" affordance off `query.isFetching` instead (true during any refetch, first load or not). `Dashboard.tsx`'s `isRefreshing` + the 2px accent line under its sticky header is the reference implementation - don't reintroduce a gate that blanks the whole screen keyed on `isLoading` alone once a query has `keepPreviousData`, and don't forget the `isFetching` signal entirely just because `isLoading` behaves better now.
- **A mutation that a user consciously triggers (Save, Delete, Import, Commit, Discard, Reorder) always gets a toast**, fired from the mutation hook's own `onSuccess`/`onError` in `api/hooks.ts` - never left to the calling component to remember, and never left silent. Call `useToast()` (`components/Toast.tsx`) inside the hook function body itself; it's a React hook like any other and the hook functions in `api/hooks.ts` already call `useMutation`/`useQueryClient` the same way. Skip it only where a screen already has its own necessarily-different feedback for that exact action (a persistent rule-creation banner in `ReviewDialog.tsx`, the type-`DELETE` destructive-action modals in `Settings.tsx`) - don't stack a redundant toast on top of those.
- **A result payload with real counts gets a real message, not a generic "Done."** `commitToastText` in `api/hooks.ts` is the pattern: build the exact sentence from the response fields ("96 committed · 8 duplicates skipped · 2 refund pairs matched"), branching on whatever's actually present rather than always listing every field.
- **`Toast` is a provider + `useToast()` hook mounted once in `main.tsx` (`ToastProvider`), not a component instantiated locally by whichever screen happens to need it first.** Before Batch 2 it was local to `AiSection.tsx` alone, so `AiSection` and `api/hooks.ts` mutations couldn't share a queue - two things firing near-simultaneously would clobber each other. The provider renders a stacked queue (`flex-col-reverse` in a fixed corner) so that's no longer possible.
- **The router is wrapped in an `ErrorBoundary` (`components/ErrorBoundary.tsx`), mounted once in `main.tsx` around `<App />`.** A render-time exception now shows a recoverable `ErrorState` instead of a blank white tab. Don't add a second, screen-local error boundary for the same failure mode - one at the root is enough; per-query `isError` branches (see the `EmptyState`/`ErrorState` rule above) are what catch *expected* fetch failures, the boundary is only for the unexpected render-crash case.
- **A slow-loading modal that the user can dismiss while it loads gets a real skeleton (placeholders sized/positioned like the eventual content), not a functioning shell around empty content.** `StagingReviewDialog`'s `StagingReviewSkeleton` (REV-7) is the reference: same `Modal` width, a real close button, three stat-card-shaped placeholders, and eight shimmer rows in the same grid columns as the real rows, all via Tailwind's `animate-pulse` - so the dialog doesn't visibly resize once data replaces the skeleton. This is worth the extra component only for a dialog whose load is slow enough to notice (an upload being parsed, an AI pass); `RecategorizeReviewDialog`'s own loading branch stays a plain line since checking for an existing pending batch is near-instant.

## The review dialog (Batch 4 - REV-1 through REV-6)

- **A `useState` updater that reads a `useRef` value from inside its callback reads it live, not as of when the updater was scheduled.** `setState((prev) => { ... ref.current ... })` defers the callback to React's next render pass; if a synchronous line *after* the `setState` call mutates that same ref (a common pattern for "remember what was clicked last"), the updater sees the *new* value, not the one that was current when the event fired. This silently broke shift-click range selection in `ReviewDialog.tsx` - `[lastClickedIndexRef.current, index]` collapsed to `[index, index]` every time, because the ref got reassigned to `index` on the very next line before the updater ever ran. Fix: capture the ref's value into a local `const` *before* calling `setState`, and close over that local in the updater instead of the ref itself. Any future ref-inside-a-setState-updater needs the same capture, not just this one - the bug has no type error and no console warning, it just silently does the wrong thing.
- **Multi-select with shift-click ranges walks the same ordered array the rows are rendered from** (`orderedRows` in `ReviewDialog.tsx`), indexed positionally - not the row's `key` or any other identity, since a range is inherently "everything between two on-screen positions." Verify a shift-click fix by checking the actual mutation outcome (which rows' data changed), not just the "N selected" count or checkbox visual state - a stale render frame can make a checkbox look unchecked for a moment even when the underlying selection set is already correct, which reads as a bug but isn't one.
- **A filter bar's tab counts are computed from the full row set, not the currently-filtered one** - "Needs review (12)" must stay 12 regardless of whether "Needs review" is the active tab, so a user can see what else is out there without clicking through every tab first. Clear the selection whenever the filter or search changes (`ReviewDialog.tsx`'s `useEffect` keyed on `[rowFilter, debouncedSearch]`) - a selection made against one filtered view silently carrying into a different one is confusing ("14 selected" for rows you can no longer see).
- **A popover mounted for one row must re-sync its local editable state when that row's committed data changes from outside the popover's own controls** - e.g. a dialog-wide "Accept all AI suggestions" bulk action touching the specific row a user happens to have open. `ReviewRowPopover`'s `category`/`label` `useState` are seeded once from `row` at mount and otherwise edited locally; without a `useEffect` re-syncing them when `row.category`/`row.matched_label` change, the open popover shows stale values that don't match the row's own badge just above it. Category re-syncs unconditionally (a `<select>` has no in-progress typing to protect); a free-text field like the label only re-syncs when there's no unsaved local edit (compare current text against the last-applied value first), so a bulk action elsewhere can't clobber what the user is mid-typing.
- **A per-field save indicator (spinner → checkmark → fade, or an error icon) belongs on each field independently**, not as one panel-wide disabled state keyed to whichever mutation happens to be in flight anywhere in the dialog. `ReviewRowPopover`'s `fieldStatus` record (one status per field key) plus `applyField()` is the pattern: never disable sibling fields while one is saving, and revert only the field that failed (its own last-good local value), not the whole row.
- **A rule-pattern suggestion is tokenised (the longest alphabetic run, uppercased), never the full raw description** - `tokenizeSuggestion()` in `ReviewDialog.tsx`. It's a rough heuristic (it can pick a common word like "PURCHASE" over the actual merchant name), not an NLP entity extractor - that's an accepted, explicit trade-off over the previous default of the entire description (reference numbers and all), which was guaranteed to never match anything again. Show the live match count next to it (batch count is free, computed client-side from rows already in memory; history count is one debounced backend call to `GET /rules/match-count`) and disable Create Rule when the total would be 1 (only the transaction the rule is being created from) - explain why via the button's `title`, don't just grey it out silently.
- **A button whose label promises a count must be labeled from the exact same array the adjoining list renders** (REV-4) - `Commit {visibleRows.length}`, not a separately-computed server field that could disagree with what's on screen or what the commit endpoint will actually write. Cross-check both halves before trusting a summary count: `commit_recategorize_batch` writes every row in `batch.rows` (scanned, not just the `changed` subset), so the honest label is `batch.rows.length`, with `batch.rows.length - batch.changed` surfaced separately as "N unchanged."

## Shell and safety (Batch 5 - X-1, X-2, X-5, X-7)

- **`Modal` (`components/Modal.tsx`) owns all dialog behaviour once, generically** - Escape to close, a Tab/Shift+Tab focus trap wrapping at the dialog's edges, autofocus on mount, focus restore to the trigger on close, `role="dialog"`/`aria-modal`/`aria-labelledby`, a background scroll lock, and a standard `×` in an optional `title` header slot. A caller opts into the header by passing `title` (a `ReactNode`, not just a string - some callers need a styled/colored heading); callers with no `title` keep rendering their own in-body heading unchanged.
  - **Capture `document.activeElement` during render, in a plain `useRef(document.activeElement)`, not inside the mount `useEffect`.** A caller's `<Input autoFocus>` applies natively during React's commit phase, which runs *before* any `useEffect` - capturing inside the effect captures the just-autofocused field, not the real trigger, so "restore focus on close" restores focus into the modal's own first field instead of back out to the page.
  - **Search for the first focusable element inside a `bodyRef`-wrapped `{children}`, not the whole dialog container.** Once a `title` header exists, its own close button is first in DOM order and would otherwise always win autofocus over the caller's actual first field.
  - **`onClose` must not be an effect dependency.** It's a fresh inline arrow function at nearly every call site; depending on it directly re-runs the mount/cleanup effect (re-capturing focus, re-adding the keydown listener) on every unrelated parent re-render while the modal is open. Stabilize it via a plain `useRef` reassigned every render (`onCloseRef.current = onClose`, not inside an effect) and keep the setup effect's own deps empty.
  - Every caller now passes `title` instead of hand-rolling its own heading `<div>` - see `Settings.tsx`'s three modals (one with a colored danger title), `Rules.tsx`'s `RuleFormModal`, `Contacts.tsx`'s `ContactFormModal`, `UploadProvider.tsx`'s `PasswordModal`, and the loading/error branches of both review dialogs.
- **A destructive action a user can trigger by mistake (rule deletion) is deferred, not instant** (X-2): hide the row immediately from a client-side pending-set (`pendingDeleteIds` in `Rules.tsx`), fire a toast with an "Undo" action button and a fixed 6s duration (`DELETE_UNDO_MS`), and only issue the real `DELETE` mutation in a `setTimeout` after that window - Undo just clears the timer and un-hides the row, no API call ever happened. `Toast`'s `ToastOptions` (`action?: { label, onClick }`, `durationMs?`) is the generic mechanism this needed; use it for any future undo-able destructive action rather than building a second one-off toast variant.
- **A reorderable list gets an optimistic mutation, not a full invalidate-and-wait.** `useReorderRules` (`api/hooks.ts`) follows the same `onMutate`/`onError`/`onSuccess` shape as `useUpdateBatchRow` (Batch 4): snapshot the previous list in `onMutate`, write the reordered list (with recomputed `priority`) immediately, roll back via the snapshot in `onError` with a toast naming what happened, reconcile via `invalidateQueries` in `onSuccess`. Drag gets a 2px accent drop indicator (`dragOverId` state, an absolutely-positioned bar above the row being dragged over) and the drag handle is independently keyboard-operable (`role="button"`, `tabIndex={0}`, `aria-label`, `Alt+ArrowUp`/`Alt+ArrowDown` calling the same `moveRule()` the mouse path uses) - don't assume drag is the only way to reorder a list; per this project's own `CLAUDE.md`, native HTML5 drag-and-drop can't be verified via browser automation (`left_click_drag` doesn't fire real `dragstart`/`drop` events), so a reorder feature needs a second, automatable path anyway.
- **The sidebar (`components/Sidebar.tsx`) expands on a genuine hover, not any incidental pointer pass, and can be pinned open.** A `HOVER_INTENT_MS` (200ms) `setTimeout` in `handleMouseEnter` gates the expand; `handleMouseLeave` clears it immediately. A `pinned` boolean (persisted to `localStorage`, key `sidebar-pinned`) and `hovering` combine into one `expanded = pinned || hovering` flag that every collapsed/expanded conditional in the component reads - never let pinned-state and hover-state visually disagree by checking them separately in different places.
  - **Pinned reserves layout space; unpinned-hover overlays.** The outer wrapper div is `w-60` when pinned (a normal in-flow sibling that pushes page content over) but stays `w-16` when unpinned (the collapsed rail's real width) even while hover-expanded - the inner panel goes `absolute` + `z-30` and grows to `w-60` only in the unpinned-hover case, overlaying content instead of reflowing it. This is intentional: hovering should never reflow the page, but pinning should.
  - **The mouse enter/leave handlers must live on the element whose own box actually changes size, not a sibling whose box stays fixed.** They were originally on the outer wrapper (fixed `w-16` even while the inner panel visually grew to `w-60`) - since the wrapper's real hitbox never grew past 64px, moving the cursor into the visually-expanded region beyond that put it outside the listener's element, triggering a `mouseleave` → collapse → `mouseenter` → re-expand oscillation. This manifested as a severe GPU-compositor tiling artifact (the whole viewport filling with repeated copies of the logo), not just a flicker - a hover handler pair on a mismatched hitbox can fail far more visibly than "the hover state is wrong." Handlers now live on the inner panel div, whose className is what actually carries the conditional width.
  - Every collapsed nav item gets a native `title={item.label}` tooltip; the active-route indicator is a `3px` accent bar pinned to the rail's own left edge (`absolute -left-3.5`), not the row's edge, so it reads identically collapsed or expanded.
- **A global `:focus-visible` rule in `index.css`** (2px accent outline, 2px offset) covers `button, a, input, select, textarea, [tabindex]:not([tabindex="-1"])` app-wide, so keyboard focus is visible without every component needing its own focus ring. Keep relying on this global rule rather than adding a per-component focus style unless a component has a genuinely different visual context (e.g. it sits on a colored surface where the default accent outline would have poor contrast).

## Data table semantics (X-6, the last item from Batch 5's scope)

- **`components/DataTable.tsx` centralizes the column *template*, not row rendering.** `DataTableColumn[]` (`key`, `header`, `width`, `align?`, `sortKey?`) drives `dataTableGridTemplate()` (a plain `"20px 24px 80px 1fr 180px 110px"` string, see below for why it's not a Tailwind class) and `DataTableHeader` (a real `role="row"`/`role="columnheader"` header, with a built-in sort-trigger button for any column carrying a `sortKey`). This is deliberately NOT a `render(row) => ReactNode` table that also owns row rendering - see the next point for why.
- **A row that's already `role="button"` keeps that role - it does not also become `role="row"`/`role="gridcell"`.** The transaction feed (`Dashboard.tsx`) and the review dialogs' row list (`ReviewDialog.tsx`, shared by `StagingReviewDialog`/`RecategorizeReviewDialog`) each render a row as a single disclosure/edit control - `role="button"`, `aria-expanded`, arrow-key navigation between rows, Enter/Space to open. That's a legitimate, already-accessible pattern (a list of expandable buttons), just not the ARIA grid-row pattern (a row containing focusable cells). Forcing `role="gridcell"` onto cells inside a `role="button"` row would misdescribe what they are without fixing a real gap - screen readers already correctly announce "button, expanded/collapsed" there. Both of those callers use `DataTableHeader` for a real column-header row (fixing the actual gap - "no column association" - for the header) and `dataTableGridTemplate` for the column template, but keep their own row markup, popover, and keyboard logic completely untouched. **Contacts.tsx is the one genuine full-grid fit** (its rows have no competing role - only the trailing edit button is interactive) - its `Card` gets `role="grid"`, and every row goes through `DataTableRow`/`DataTableCell` for real `role="row"`/`role="gridcell"` semantics end-to-end. Give any *new* list this same test before reaching for `DataTable`'s row/cell wrapper: if the row itself is (or should be) independently focusable/actionable as a single unit, wrap only the header; if a row is just a container of independently-focusable cells with no click behavior of its own, use the full row/cell wrapper.
- **A literal duplicated grid-cols string (typed out twice, header and row, kept in sync by hand) is the concrete bug this fixes** - Contacts.tsx had exactly that. The transaction feed and the review row list had already converged on a single shared constant (`FEED_GRID_TEMPLATE`/`ROW_GRID_TEMPLATE`) before this - `dataTableGridTemplate(columns)` replaces the hand-typed string in both cases with one computed from the same array `DataTableHeader` renders from, so the two can't drift even if a future column gets added to one but not the other.
- **A column template built at runtime is applied via inline `style={{ gridTemplateColumns }}`, never a `grid-cols-[...]` Tailwind class - this was a real, severe bug, not a style preference.** `dataTableGridTemplate()` originally returned a `grid-cols-[${...}]` *class name*. Tailwind only generates CSS for an arbitrary-value class that appears as a complete, literal substring somewhere in the source it statically scans; a class assembled from an array at runtime never does, so that class had **no matching CSS rule at all** - every consumer (the feed, Contacts, both review dialogs) silently rendered as a single collapsed column instead of a grid. It went undetected through most of a session's testing purely because Tailwind's dev-mode output is additive: an earlier *literal* version of the same string (from before these were extracted into `DataTable.tsx`) was still sitting in the generated stylesheet, and only a dev-server restart or a real production build - both of which scan fresh - exposed it. See `CLAUDE.md`'s "Frontend gotchas" for the full mechanism. The fix: `dataTableGridTemplate()` now returns a bare value string (`"20px 24px ..."`), and every caller sets it via `style={{ gridTemplateColumns: ... }}` alongside a plain `className="grid ..."` with no arbitrary-value class in it. If a column template is ever fully static (hardcoded, never built from an array/prop), a literal `grid-cols-[...]` class is fine - the constraint is specifically about anything computed at runtime.
- **A `position: sticky` element inside a scroll container needs an explicit `z-index` if anything else in that same container can visually reach it while scrolling.** `ReviewDialog.tsx`'s sticky column header had none; once AI categorization was genuinely running (not just failing fast against an unreachable model, which is all local testing had exercised), the "AI is categorizing…" banner and the pending rows' `Sparkles` icon/skeleton shimmer - later DOM siblings in the same scroller - painted *over* the header instead of staying under it, because a sticky element with no `z-index` has stacking level `auto` and paints in plain DOM order like anything else. Fixed with `z-10`, matching the pattern the dashboard feed's own sticky header already used. Give any new sticky header in a scrolling list the same `z-10` up front rather than waiting to notice the overlap.
- **A row-list's own scroll region gets a fixed height (`h-[Npx]`/`h-[Nvh]`), not a max-height (`max-h-...`), if the dialog/card around it should never resize based on how many rows are currently visible.** `ReviewDialog.tsx`'s row scroller was `max-h-[45vh]` - a *cap*, not a height - so filtering down to a handful of rows shrank the scroller (and the whole dialog around it) to fit just those rows. `h-[45vh]` always reserves the same space regardless of window size; a short filtered/searched result just leaves empty space in it instead of collapsing the box. Reach for `max-h` only when the container's height should genuinely track its own content up to some ceiling - not for a list living inside a dialog whose overall size should track the window, unaffected by filtering.
- **A large row list (a big multi-file upload can mean hundreds of rows) must not force React to re-render every row on every unrelated state change.** `ReviewDialog.tsx`'s row list used to build each row's JSX inline inside one `.map()` in the dialog's own render function - toggling one checkbox or opening one row's popover meant React re-ran that render logic for *every* row, not just the one that changed, which read as a general slowness/laggy-checkbox problem on a large batch. Fixed by extracting `ReviewRowItem` as its own `memo()`-wrapped component, with `isOpen`/`checked`/`pending` passed down as plain booleans computed by the caller (`selectedKeys.has(row.key)`, not the `Set` itself) so `memo`'s shallow prop comparison can tell "this row's own state changed" apart from "some other row's state changed" - the latter must leave a given row's props byte-for-byte identical or the whole optimization is void. The filter/sort/group derivations that feed the row list (`filterCounts`, `visibleRows`, `aiPendingRows`, `otherRows`, `orderedRows`) are all `useMemo`'d for the same reason - none of them should be recomputed just because a checkbox or `openKey` changed elsewhere in the same component. Give any new large, interactive list this same shape: primitives (not collections) as row props, and `memo()` on the row component, before reaching for anything heavier like virtualization.
- **Driving a checkbox's selection state off `preventDefault()` + a wrapper `onClick`, instead of the checkbox's own `onChange`, is a real source of visual desync, not just an unusual pattern.** The row-select checkbox used to call `e.preventDefault()` in a wrapping div's `onClick` (to cancel the native toggle) and drive `toggleSelect` from that same handler, leaving the `Checkbox`'s own `onChange` a no-op. This left a real gap where the DOM's native `checked` state could end up out of step with React's controlled value, only resolving itself once some *other*, unrelated re-render happened to touch that node again - it read as "the checkbox doesn't visually update until I click something else." Fixed by letting the native click/toggle happen normally and driving selection off the checkbox's real `onChange`; a shift-click range-select still needs the modifier key, captured via `onMouseDown` on the wrapping div (which always fires before click/change) into a ref, since `ChangeEvent` carries no modifier keys even though a checkbox's `onChange` is implemented on top of its click event. Don't fight a native control's own event with `preventDefault` when you can just read the authoritative result from its real change event instead.

## AI categorization progress (no server-side timeout, a live timer, a real Cancel)

- **A background job with no natural time bound should not have an arbitrary server-side timeout that silently falls back on the user's behalf.** Every AI provider's `categorize()` call (`ai_providers/ollama.py`/`openai_compatible.py`/`anthropic.py`) used to have a flat 90s `CATEGORIZE_TIMEOUT`, long enough to matter for a big local-model batch but with no way to just wait longer - it silently fell back to rules-only with a generic "the request failed" warning. The Cancel action described below is what replaces the timeout as the actual escape hatch.
- **A long-running background job the user can watch should show elapsed time from a fixed start anchor, ticked locally - not derived from how often the batch happens to be polled.** `StagingBatch`/`RecategorizeBatch` both carry an `ai_started_at` timestamp, set the moment the background task is scheduled and cleared on any terminal status. `ReviewDialog.tsx`'s `AiRunningTimer` reads that once and ticks its own `setInterval` off `Date.now() - startMs` - a small, separately-`memo`-able concern, not something wired through the batch's own 1.5s poll interval (`useCurrentStagingBatch`'s `refetchInterval`), which is plenty for catching `ai_status` leaving `"running"` but far too coarse for a readable second-by-second clock.

Cancellation itself is only ever best-effort (closing the underlying `httpx.Client` interrupts a blocked read on most platforms, but not guaranteed everywhere - see `ai_providers/cancellation.py`'s own docstring), so `job_runner.py`'s existing "batch still exists" race guard around each `get_batch()` re-fetch was widened to also check `ai_status == "running"` - a call that wasn't actually interrupted and runs to completion anyway must see its own batch is no longer `"running"` and back off, rather than silently overwriting `"cancelled"` with `"done"`.
- **A dialog that dumps a raw list into its subtitle (every uploaded filename, comma-joined) should show a compact summary instead, with the full detail in a native `title` tooltip.** `StagingReviewDialog`'s subtitle used to be `batch.source_filenames.join(', ')` - fine for one file, an unreadable wall of text for a large multi-file upload. It's now `"{name}"` for exactly one file or `"{n} statement files"` otherwise, wrapped in a `<span title={...}>` carrying the full comma-joined list for anyone who actually needs it.

## Destructive row actions

- **A row's delete goes through `lib/useUndoableDelete.ts`, never a hand-rolled copy.** The gesture is fixed: hide the row immediately, toast with an Undo action, and only send the DELETE once the undo window (`DELETE_UNDO_MS`, 6s) closes. Rules and the transaction feed each carried their own byte-identical implementation of this - one of them with a comment explaining why a shared constant wasn't worth it - and Contacts would have made three, which is where a retyped shape becomes a primitive (root cause 01). Call it as `useUndoableDelete('Contact', deleteContact.mutate)` and filter the list on the `pendingIds` it hands back. Keep that hidden set as its own state rather than writing optimistically into the query cache: Rules composes its reorder payload from the cached list, and the backend rejects a reorder that doesn't name every non-default rule, hidden-but-not-yet-deleted ones included.
- **The pending set and the commit timers live in `components/UndoableDeleteProvider.tsx`, above the router - not in the page.** When they were page state with an unmount cleanup, leaving the page inside the undo window cleared the timer (the delete was silently dropped and the row came back on the next visit) and a quick return re-mounted the page with an empty pending set (the row reappeared, then vanished when the timer fired). The toast is already app-level and keeps its Undo button live across the navigation, so the state backing it has to be too. The deferred `mutate` still invalidates its query cache after the calling page unmounts because that side effect is on `useMutation`, not on the `mutate` call.
- **A row action is an icon with a `title` and an `aria-label`, not a text button.** Rules' delete was the last word-label action left in a row; at the end of a row of icons it read as a different kind of control from the pencil beside it. `Trash2` at `size={13}`/`size={14}`, `text-muted-2 hover:text-danger-text`, and an `aria-label` that names the row ("Delete Sample Payee C") so the control is distinguishable when every row's icon is otherwise identical.

## Opening things outside the browser

- **An endpoint that shells out takes no path from the request.** `POST /api/data-lifecycle/reveal` opens the database's folder in Finder/Explorer/the desktop file manager, and builds its argv from `get_db_path()` and nothing else - there is no path parameter to smuggle anything through, and the command is a list, never a shell string. `tests/test_reveal_db_folder.py` pins both, plus the per-platform verb.
- **It answers, it doesn't raise.** A machine with no desktop session (a server-hosted copy, a container) genuinely has nowhere to open a folder; that's `{opened: false, error: "..."}` and an inline toast, not a 500. The path is already printed on the Settings page, so the fallback is "open it yourself", which the error says.
- **Name the file manager in the label.** "Show in Finder" / "Show in Explorer" / "Show in Files" makes it obvious the click leaves the browser in a way "Open Folder" doesn't. The frontend picks the word from the user agent (a wrong guess costs a slightly odd label); the backend picks the real command from `sys.platform` independently.

## Wide windows (the app has a minimum width and now a maximum too)

- **Every page's content column is bounded and centred, never left to stretch with the window.** `PageShell` defaults `maxWidth` to `max-w-page` (`--container-page`, 1600px, defined in `index.css`) and adds `mx-auto`; `Dashboard.tsx` carries the same pair by hand since its header is the sticky exception. A page that wants a *narrower* measure still passes its own (`Settings` at `max-w-4xl`, `Guide` at `max-w-3xl`) — what no page should do is opt out of a bound entirely. Nothing on any of these screens gets denser as the window widens: the dashboard shows four metrics, two charts and one feed at 1280px and exactly the same at 2560px, so an unbounded column just stretched each component around unchanged content — a metric card 600px wide holding a label and a number, a feed row with 1200px of nothing between its description and its category. `NarrowWindowNotice`'s `MIN_WIDTH` states the floor; this states the ceiling.
- **A component handed extra width must use it, not centre a fixed-size thing in it.** Two ways to do that, both already in the codebase: let the content scale (`CashFlowChart`'s bars are `flex-1` with a per-month-count `max-w-*` cap, not a fixed `w-*` — fixed widths drew two 14px slivers marooned in a 150px column on a large screen), or give the row something proportional to fill with (`CategoryDonut`'s legend rows and `RankedBarRow` both draw a bar sized against the largest entry). Stretching a row *without* either — the category legend's first attempt, `flex-1` and nothing else — is worse than not stretching it, because it strands each percentage a few hundred pixels from the name it belongs to.
- **Scale a proportional bar against the largest row actually rendered, including any aggregate.** `CategoryDonut`'s "Other (n)" total can exceed every individual slice; scaling to `data[0].pct` alone clamped both to full width and made a 24% aggregate and a 20.9% top category read as equal.

## Scroll shadows

- **A sticky element's drop shadow must be conditional on something actually being scrolled underneath it** — `lib/useScrolledUnder.ts` returns `[scrolled, ref]` for exactly this, and the shadow class goes in a template literal gated on `scrolled`. Drawn unconditionally, a `shadow-[0_4px_6px_-4px_rgba(0,0,0,0.4)]` paints ~6px of shadow onto whatever sits directly below the sticky element *at rest*: a sticky header's own bottom padding is inside its box, so there is no gap for the shadow to land in and it darkens the top edge of the first card instead, which reads as the header overlapping the card rather than as depth. This was live on the Dashboard's page header, its feed column header, and `ReviewDialog`'s row header; all three are gated now, with `transition-shadow` so it fades rather than snaps.
- **`useScrolledUnder` returns a callback ref, and that's load-bearing.** The headers that want it usually render only after their page's first data arrives (the Dashboard renders a loading sentence on its first pass), so an effect keyed on `[]` would run against `ref.current === null` and never subscribe to anything. A callback ref fires whenever the node actually attaches. Where a caller needs the node for something else too — the feed's column header is also measured for the month dividers that stick below it — merge the two in a `useCallback`, don't pass an inline arrow (a new function identity each render makes React detach and re-attach the ref, re-running the subscription every time).
