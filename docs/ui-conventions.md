# UI Conventions

Living document. Grows section-by-section as `UI Review.dc.html`'s findings get fixed (see root of repo — the source review this doc is remediating). Each rule below exists because a real instance of it was found and fixed; the rule is what stops it from coming back. When a future UI review finds something new, add the fix *and* the rule here in the same change.

Unlike `docs/technical-spec.md`/`docs/ux-spec.md` (frozen pre-implementation design docs), this file is meant to be edited as the UI evolves — it's a checklist, not a historical record.

## Data tables / lists (transaction feed, review dialogs, contacts, rules)

- **A fixed-width column that holds icon+text (category badges, account names) must truncate, never wrap.** A wrapped cell is taller than its neighbours, and a scrolling list where row heights jitter is one of the most visible forms of jank an app can have. Give the cell `truncate` (or `whitespace-nowrap overflow-hidden text-ellipsis`) plus a `min-w-0` ancestor (grid/flex children don't shrink below content size by default) and a `title` attribute so the full value is still reachable. `CategoryBadge.tsx` is the canonical example — it truncates its label and always sets `title={category}`.
- **A long, unbounded list (>~200 rows) must paginate or virtualize — never render everything into one growing DOM list.** Page at 100 rows with a "Load more (N remaining)" control at the bottom; reset the page size back to 100 whenever the underlying filtered/sorted set changes (a stale larger page size can silently show more than a fresh filter should).
- **A sticky column header inside a long list needs its own bounded, independently-scrolling container** (`max-h-[Npx] overflow-y-auto` wrapping just the header + rows, with the header itself `sticky top-0`) — not a page-level `sticky top-0` on the header that requires measuring and subtracting some *other* sticky element's height. The bounded-container approach needs no JS measurement, doesn't depend on how tall a page-level header happens to render, and is proven in both `ReviewDialog.tsx`'s row list and `Dashboard.tsx`'s transaction feed. If you truly need a second sticky layer inside that same container (e.g. a month divider under the column header), measure *only* the sibling sticky element's own height via a `ref` + one-time `useEffect`, not the whole page.
- **A date-sorted list spanning multiple months should insert a sticky divider row per month** ("August 2026 · 104 transactions · $4,182 out") rather than letting identical-looking date labels repeat with nothing separating them. Only render dividers while the list is actually sorted by date — they're meaningless (and misleading) once sorted by anything else.
- **Any date shown in a list needs the year included whenever the active range spans more than one calendar year** (`fmtDate(iso, { withYear: true })`). A bare "Aug 28" is ambiguous the moment two different years are both in view.

## Money

- **Always render the sign, never encode direction through color alone.** Use `fmtSigned` (`+$12.34` / `-$12.34`), not `fmtPlain(Math.abs(x))` colored differently. Color is a reinforcing signal, not the only channel for the single most important fact in a transaction row.
- **Use exactly two fixed colors for amounts** — `text-success` for inflow (positive), `text-text` (the default reading color) for outflow. Do not derive a continuous/interpolated color from the amount's magnitude (a retired helper, `amountIntensityColor`, did this via `oklch()` + `log1p` scaling — at low magnitudes the chroma dropped low enough that a $10 debit and a $10 credit were nearly indistinguishable). If magnitude needs its own visual signal, use `font-semibold` above a threshold (e.g. ≥50% of the max amount currently in view) — weight is legible at a glance in a way a subtle hue/chroma shift is not.
- **Every numeric figure rendered in `font-mono` gets tabular figures for free** — `index.css` sets `font-variant-numeric: tabular-nums` on the `.font-mono` utility globally. Don't reach for a per-component numeric class; just use `font-mono` on any stacked/aligned number the way the rest of the app already does.

## Filters (any page with more than one filter control)

- **Every filter a user can set must be visible on screen while it's active, not just reachable through the control that set it.** A category filter set by clicking a donut slice, with the category `<select>` scrolled out of view, silently shrinks a list with zero visible explanation. Render active filters as dismissible chips ("Category: Groceries ×", "Search: kopitiam ×") near the list they affect, with a "Clear all" once more than one is active.
- **Every filter that affects a page's main content must persist across reloads (localStorage) *and* be mirrored in the URL query string**, so a filtered view is both remembered and shareable/bookmarkable. See `lib/dashboardFilters.ts` (`loadDashboardFilters`/`saveDashboardFilters`) paired with `useSearchParams` in `Dashboard.tsx`'s `persist()` — URL params win on initial load (a shared link should show what it promises), falling back to localStorage, falling back to a hardcoded default. Use `{ replace: true }` when writing search params on every keystroke/toggle so filtering doesn't spam browser history.
- **A live-filtering text search must be debounced (150ms is the standard used here)** and should search every field a user would reasonably expect a match against — not just the one or two fields that happened to be easy to add first. For the transaction feed that's label, raw description, category, account, and the formatted amount.

## Row interactivity / accessibility

- **A row that's clickable must also be keyboard-reachable and announce itself as interactive**: `role="button"`, `tabIndex={0}`, an `onKeyDown` handling `Enter`/`Space`, a `hover:` background, and a `focus-visible:outline` — not just `onClick` on a bare `div`. See the transaction feed row in `Dashboard.tsx`.
- **Any nested interactive control inside a clickable row must `e.stopPropagation()` in its own `onClick`**, or it will also trigger the row's click handler (double-fire at best, wrong action at worst — e.g. a refund-link button inside a row that opens the row's own editor when clicked).
- **A hover-only affordance (an edit pencil, etc.) should still be faintly visible at rest** (`opacity-40`, not `opacity-0`) so the row communicates it's editable before the user happens to hover it. Full opacity on `group-hover`/`group-focus-within` as before.

## Primitives and tokens (Batch 1 - root causes 01 and 02)

- **A "form action" button (Cancel/Save/Confirm/Discard in a modal or card footer) always goes through `components/Button.tsx`**, never a hand-rolled `<button className="...">`. Five near-identical padding variants (`px-4 py-2.5`, `px-5 py-2.5`, `px-4.5 py-2.5`, `px-3.5 py-2`, `px-3 py-2`) existed at ~40 call sites before this; `Button` collapses them to two sizes (`md` default, `sm`) and five variants (`primary`, `secondary`, `danger`, `danger-outline`, `ghost`). Bespoke controls that aren't really "a labelled button" - `Select`'s trigger, `Tabs`, calendar day cells, `Sidebar` nav items, icon-only affordances like a row's edit pencil - stay their own components; forcing those through `Button` would fight its variant set for no consistency win.
- **A standard text input goes through `components/Field.tsx`'s `Input`**, not the repeated `"w-full box-border px-3 py-2.5 rounded-lg border border-border bg-input text-text text-md"` string (~15 call sites before this). Pass `mono` for the handful that also hand-added `font-mono` (paths, DELETE-to-confirm fields, rule patterns, API keys). A handful of intentionally denser inputs (the review popover's compact fields, `px-2.5 py-1.5`) stay hand-rolled rather than fighting `Input`'s padding - see the note below on why overriding padding/width through `className` isn't safe.
- **Never pass a `className` override that fights a primitive's own width/padding utility** (e.g. `<Input className="w-[240px]">` when `Input` already sets `w-full`). Two Tailwind utilities targeting the same CSS property (`width`, `padding-inline`, ...) both end up in the generated stylesheet, and which one wins is decided by Tailwind's internal generation order, not by position in the `className` string - relying on "mine comes later" is not safe. `Input` instead takes an explicit `fullWidth={false}` prop that omits `w-full` entirely, so there's only ever one width utility active. Give any future primitive the same escape hatch (a boolean/variant prop) rather than trusting a className override to win a specificity tie.
- **A settings/summary card wrapper goes through `components/Card.tsx`**, not a repeated `"bg-card border border-border rounded-xl p-5"` div. Pass `padding=""` for a list container whose rows supply their own padding (`overflow-hidden` table-like lists), or `padding="p-4.5"` for the one tighter metric-card variant - both replace the whole padding class rather than layering a second one, so there's no width/padding conflict.
- **A page header (title, optional subtitle, optional right-aligned actions) goes through `components/PageShell.tsx`**, matching the `px-9 pt-7 pb-15` + `text-title font-bold font-display` shape every page already converged on by convention before this, now shared instead of retyped. `Dashboard.tsx` is the one exception - its header is `sticky` with its own scroll-tinted background, a genuinely different layout, not just a restyle.
- **`EmptyState`/`ErrorState` (`components/EmptyState.tsx`) exist for the "no data" vs. "the backend is down" distinction** (root cause 04 / X-4 in the review doc). As of Batch 2 they're wired into the six places the review named - Rules, Contacts, Default Rules, the Dashboard feed, and both review dialogs (via `ReviewDialog.tsx`'s own empty-row rendering, shared by staging and recategorize) - each with an `isError`/`onRetry` branch calling the query's own `refetch()`. A *new* list screen still needs to wire these in itself; they don't apply themselves.
- **Semantic color literals never get hand-derived per component.** `index.css` defines tinted-surface tokens for each of the four recurring states - `--color-warning-*` (amber, "needs review"), `--color-ai-*` (violet), `--color-success-*` (green), `--color-danger-*` (red) - each with a `-surface`/`-surface-border` pair for banners and a `-badge-bg`/`-badge-fg` pair for pills/badges. Before this, `ReviewDialog.tsx` alone had six local `oklch()` constants, and `PendingReviewBanner`/`Rules`/`Settings`/`AiSection`/`Toast` each re-derived their own near-identical values. A category's *own* color is the one legitimate exception (`lib/categoryColor.ts` computes `oklch()` from a per-category hue) - that's inherently data-driven, not a fixed semantic state, so it can't be a static token.
- **A one-off pixel font size only gets a new token if it doesn't already match a Tailwind default.** `text-[12px]` is exactly `text-xs` - use that, no new token needed. Sizes with no default home (11px, 13px, 15px, 22px) get non-colliding custom names - `text-2xs`, `text-md`, `text-title-sm`, `text-title` - deliberately *not* named `xs`/`sm`/`base`/`lg`, so adding them can never silently reflow the ~85 call sites already using Tailwind's own default scale at their default sizes. The same logic applies to radii: `rounded-md`/`lg`/`xl`/`2xl` already matched this app's 6/8/12/16px scale at Tailwind's defaults and needed no new token; only the one true outlier (`rounded-[10px]`, homeless between `lg` and `xl`) got a new `rounded-2lg`.

## Async behavior (Batch 2 - root causes 03 and 04, X-3, X-4, DASH-1, REV-7)

- **A query whose key changes on user interaction (a filter, a date range, an account picker) must set `placeholderData: keepPreviousData`** (from `@tanstack/react-query`). Without it, TanStack Query resets `data` to `undefined` and `isLoading` to `true` on every key change, which is what caused the Dashboard's entire page to blank out on every range/account change (root cause 03 / DASH-1) - `useDashboardSummary`, `useTransactions`, and `useMonthlyTotals` in `api/hooks.ts` all set it now. The `QueryClient` in `main.tsx` also sets a global `staleTime: 30_000` so navigating back to an already-fresh screen doesn't refetch-and-flash either; that's a separate, complementary fix - `staleTime` does nothing for the query-key-changed case, only `keepPreviousData` does.
- **Distinguish "nothing to show yet" from "still updating."** With `keepPreviousData` in place, `query.isLoading` only stays true on the true first-ever load (nothing cached, nothing to render) - keep that as a real loading gate, but drive any "this is refreshing" affordance off `query.isFetching` instead (true during any refetch, first load or not). `Dashboard.tsx`'s `isRefreshing` + the 2px accent line under its sticky header is the reference implementation - don't reintroduce a gate that blanks the whole screen keyed on `isLoading` alone once a query has `keepPreviousData`, and don't forget the `isFetching` signal entirely just because `isLoading` behaves better now.
- **A mutation that a user consciously triggers (Save, Delete, Import, Commit, Discard, Reorder) always gets a toast**, fired from the mutation hook's own `onSuccess`/`onError` in `api/hooks.ts` - never left to the calling component to remember, and never left silent. Call `useToast()` (`components/Toast.tsx`) inside the hook function body itself; it's a React hook like any other and the hook functions in `api/hooks.ts` already call `useMutation`/`useQueryClient` the same way. Skip it only where a screen already has its own necessarily-different feedback for that exact action (a persistent rule-creation banner in `ReviewDialog.tsx`, the type-`DELETE` destructive-action modals in `Settings.tsx`) - don't stack a redundant toast on top of those.
- **A result payload with real counts gets a real message, not a generic "Done."** `commitToastText` in `api/hooks.ts` is the pattern: build the exact sentence from the response fields ("96 committed · 8 duplicates skipped · 2 refund pairs matched"), branching on whatever's actually present rather than always listing every field.
- **`Toast` is a provider + `useToast()` hook mounted once in `main.tsx` (`ToastProvider`), not a component instantiated locally by whichever screen happens to need it first.** Before Batch 2 it was local to `AiSection.tsx` alone, so `AiSection` and `api/hooks.ts` mutations couldn't share a queue - two things firing near-simultaneously would clobber each other. The provider renders a stacked queue (`flex-col-reverse` in a fixed corner) so that's no longer possible.
- **The router is wrapped in an `ErrorBoundary` (`components/ErrorBoundary.tsx`), mounted once in `main.tsx` around `<App />`.** A render-time exception now shows a recoverable `ErrorState` instead of a blank white tab. Don't add a second, screen-local error boundary for the same failure mode - one at the root is enough; per-query `isError` branches (see the `EmptyState`/`ErrorState` rule above) are what catch *expected* fetch failures, the boundary is only for the unexpected render-crash case.
- **A slow-loading modal that the user can dismiss while it loads gets a real skeleton (placeholders sized/positioned like the eventual content), not a functioning shell around empty content.** `StagingReviewDialog`'s `StagingReviewSkeleton` (REV-7) is the reference: same `Modal` width, a real close button, three stat-card-shaped placeholders, and eight shimmer rows in the same grid columns as the real rows, all via Tailwind's `animate-pulse` - so the dialog doesn't visibly resize once data replaces the skeleton. This is worth the extra component only for a dialog whose load is slow enough to notice (an upload being parsed, an AI pass); `RecategorizeReviewDialog`'s own loading branch stays a plain line since checking for an existing pending batch is near-instant.
